1. 背景与候选方案全景

1.1 SQLite 为何没有官方免费加密

1.1.1 商业 SEE 留下的生态空位

SQLite 本体以公有领域（Public Domain）形式发布，核心库不含任何加密能力。其开发方 Hwaci 将静态数据加密做成了独立的商业产品 SEE（SQLite Encryption Extension）：一次性 US$2000 的源码许可，自 2007 年起销售，随 SQLite 官方版本持续维护[51][135]。SEE 以替换 sqlite3.c 合并源文件（amalgamation）的方式交付，同系列的 CEROD（只读加密）与 ZIPVFS（压缩加密 VFS）分别标价 US$2000 与 US$4000[51]。"官方加密只此一家且收费"这一格局，直接催生了一个持续十余年的第三方免费/开源加密生态——从早期的 wxSQLite3 codec、System.Data.SQLite 的 RC4 方案，到 2008 年出现的 SQLCipher，再到 2024 年后自带加密的 libSQL/Turso fork。

1.1.2 三条技术挂接路线

SQLite 加密扩展本质上只有三种挂接点，所有候选方案都可归入其一：

  • codec 内部钩子：官方源码预留 SQLITE_HAS_CODEC 编译开关，打开后暴露 sqlite3_key() / sqlite3_rekey() API，通过内部函数 sqlite3pager_set_codec() 把加解密回调挂到 Pager 上，读页解密、写页加密[143][144]。SQLCipher 官方明确指出这条路无法用可加载扩展实现——"将 codec 回调挂到 pager 的第一步就依赖内部 API"，因此此类方案必须以替换 amalgamation 的方式整体构建[2]。
  • VFS 层拦截：在虚拟文件系统（Virtual File System）层包装底层 I/O，对落盘字节流透明加解密，不触碰 pager 内部结构。
  • fork / 重写原生集成：直接把加密做进数据库引擎内部（libSQL fork 与 Rust 重写的 Turso Database），加密成为引擎一等特性而非外挂。

1.3 生态格局演进

1.3.1 SQLite 3.32 断代事件

2020 年 5 月发布的 SQLite 3.32.0 移除了长期存在但从未文档化的 SQLITE_HAS_CODEC 编译选项（官方 changelog 原话："Simplify the code by removing the unsupported and undocumented SQLITE_HAS_CODEC compile-time option"），所有依赖 codec 内部钩子的补丁式方案瞬间失去升级路径[48]。最典型受害者是 sqleet：代码永久停留在 SQLite 3.31.1，作者于 2023 年正式宣布停更，并在 README 中推荐用户转向 wxSQLite3（其提供 sqleet 兼容加密格式）[57]。同一事件也终结了 System.Data.SQLite 的官方 RC4 加密支持[48]。幸存者的分化清晰勾勒出格局迁移方向：utelle 于 2020 年 8 月推出独立项目 SQLite3MultipleCiphers，改走 VFS 层实现以摆脱对内部 API 的依赖[48][45]；libSQL/Turso 则干脆以 fork/重写的方式把加密做成引擎原生能力[56][55]。生态由此完成从"codec 补丁"向"VFS hook 与 fork 原生集成"的重心转移。

1.3.2 2026 年：一超、一强、一新

综合 Star 数、下游覆盖与维护活跃度，2026 年的开源格局已收敛为三层结构。一超：SQLCipher（7,213 星，BSD-3），移动端事实标准，靠商业版（$999 起）与 Enterprise/FIPS 计划变现，社区版功能被刻意限定在核心加密[52][14]；一强：sqlite3mc（661 星，MIT），Star 数不高但下游工具链覆盖最广、更新频率最高（2026-07-25 仍有提交，v2.4.0 跟踪至 SQLite 3.53.4），且其 legacy 模式可读写 sqleet 与 SQLCipher v1–v4 文件，是唯一具备"格式逃生舱"的方案[122][28][32]；一新：Turso Database（23,431 星，MIT），Star 数断层领先，原生 AEAD 加密读开销官方宣称约 6%，但加密仍为 experimental、无第三方工具链可打开其加密文件，且未经第三方安全审计[53][55][79]。对生产选型而言，成熟路径只有 SQLCipher 系与 sqlite3mc 系两条；Turso 适合新项目试水，但须接受"只能用 Turso 引擎打开"的文件格式锁定。后续章节将逐层剖析这三条路线的原理、性能与接入方式。

2.1 SQLCipher：事实标准

项目现状。 SQLCipher 由 Zetetic LLC 于 2008 年发布并持续维护至今，官方自述部署量达数亿设备、覆盖数千家组织[6]。截至快照日，仓库 7,213 Stars、1,394 Forks、open issues 仅 8 个，许可证 BSD-3-Clause[23]。最新版本 v4.17.0 发布于 2026-07-08，年内已发 4.13.0→4.17.0 共 5 个版本，最近提交为对齐上游 SQLite 3.53.3 的源码快照[52][4]——官方自称每年 3–6 次发版，实测节奏完全吻合[6]。它不是 SQLite 的可加载插件，而是直接修改 SQLite 源码、独立维护的源码树，每个 release 基线对齐特定上游 SQLite 版本[1]。

加密体系。 SQLCipher 采用逐页（page-level）加密：算法为 256 位 AES 的 CBC 模式，默认页大小 4,096 字节；每页拥有由密码学安全随机数生成器产生的独立随机初始化向量（IV），存于页尾并在每次写入时重新生成；每页写入附带覆盖密文与 IV 的 HMAC-SHA512 认证码，读取时校验[1]。密钥派生（KDF）为 PBKDF2-HMAC-SHA512，默认 256,000 次迭代，每个数据库在文件头前 16 字节存入唯一随机盐[1]。SQLCipher 不自研密码学原语，而是外挂 OpenSSL libcrypto 或 CommonCrypto；曾支持的 LibTomCrypt 与 NSS 两个 provider 已在 v4.12.0（2025-12）正式移除[1][3][7]。

社区版与商业版差异。 社区版以 BSD-style 许可发布，可免费用于开源及闭源商业软件，但要求在产品用户可见处保留归属声明[18]。官方功能矩阵显示：社区版仅含整库加密；Commercial（$999/应用/年起，且限定公司年收入低于 $50M）增加优化密码学实现（官方宣称比社区版快至 4 倍）、Value Level Encryption（VLE，字段级加密 SQL 函数）、加密虚拟表、性能计数器与 benchmark 工具[14][19][20]；Enterprise 独占 Cordova/JDBC/React Native/Apple WatchKit 等平台包、SLA 保障响应与定制构建，FIPS 140-3 验证模块仅随 Enterprise FIPS 包提供——标准与社区版无论操作系统设置如何均非 FIPS 验证[21][5]。知名采用者包括 Signal（维护自有 fork）与 Salesforce SmartStore[22]。

2.2 sqleet 与 SQLite3MultipleCiphers

sqleet：开创 ChaCha20 路线，但未归档却实质停更。 sqleet 仓库 394 Stars、57 Forks，许可证为公有领域 Unlicense[57]。此处需要精确表述其状态（交叉验证 Conflict Zone 3）：GitHub API 显示 archived=false，即未归档；但 README 自认 unmaintained——因上游 SQLite 废弃 codec API，sqleet 卡死在 SQLite 3.31.1，等待重大重写，作者明确推荐改用 utelle 的 wxSQLite3（提供 sqleet 兼容加密）[25]。最后一次代码推送为 2023-05-03，最后一个 release 为 v0.31.1（2020-01-28）[57][26]。其密码学设计三要素为：PBKDF2-HMAC-SHA256 密钥派生（16 字节盐、12,345 次迭代）、ChaCha20 流密码（每页一次性密钥）、Poly1305 认证标签；整个加密文件（含 header）与随机数据不可区分[25]。工程上它零外部依赖、release 包中的 sqleet.c/h 是官方 sqlite3.c/h amalgamation 的 drop-in 替换，这是它当年被广泛内嵌的原因[25]。需如实指出数据缺口：sqleet 官方 README 无任何量化 benchmark，仅有"现代高性能密码学"的定性声明，网传"README 有 benchmark"未获证实[25]。

SQLite3MultipleCiphers：sqleet 官方推荐的事实继任者。 sqlite3mc 仓库 661 Stars、103 Forks，MIT 许可，open issues 仅 2 个；最近 push 为 2026-07-25（调研前一日），同日发布 v2.4.0（基于 SQLite 3.53.4），2026 年内已发 2.2.6→2.4.0 共 8 个版本，节奏紧随 SQLite 官方[27][28]。其继任者地位有双重佐证：sqleet 作者在 README 亲自指向 utelle 项目，且 sqleet cipher 被 sqlite3mc 设为默认 cipher scheme[25][29]。sqlite3mc 共支持 7 种 cipher scheme：wxSQLite3 AES-128/256-CBC（无 HMAC，不推荐新用）、sqleet ChaCha20-Poly1305（默认）、SQLCipher v1–v4 全系列（AES-256-CBC + SHA1/256/512 HMAC）、System.Data.SQLite RC4（仅兼容旧库）、Ascon-128 v1.2、AEGIS 家族（Argon2id KDF）[29][30]。实现上它不再使用已被 SQLite 3.32.0 移除的 codec API，而是作为 VFS 层扩展工作，兼容 SQLite ≥ 3.32.0[30][45]。默认 ChaCha20 cipher 的 KDF 迭代数已从 sqleet 的 12,345 提升至 64,007（legacy 模式仍保留旧值以兼容原 sqleet 文件）[31]。相比 SQLCipher 需 ATTACH + sqlcipher_export 整库复制，sqlite3mc 的 rekey 通过修改版 VACUUM 原地完成加密/换 cipher/解密[38]。项目无任何商业层，完全由作者 utelle 个人维护。

2.3 wxSQLite3

wxSQLite3 与 sqlite3mc 同出 utelle 之手，仓库 652 Stars，许可证 LGPLv3 附带 wxWindows 3.1 例外（允许静态链接于闭源应用）；最新版本 4.12.5（2026-06，升级 sqlite3mc 2.3.5 / SQLite 3.53.2），最近 push 2026-07-16，维护活跃[49][48]。它的历史角色大于当下角色：自 1.7.0 起内置基于密钥的 AES 加密扩展，早期 AES-128 还是 AES-256 为编译期决定，4.0.0 起才支持运行时选择[48]。其原生 legacy 加密为 AES-128/256-CBC 且无 HMAC——即只提供机密性、不提供防篡改完整性校验，这是它与 SQLCipher 的关键历史差距，官方文档也已不推荐新应用使用该 scheme[48][30]。转折点是 SQLite 3.32.0（2020-05）移除了非文档化的 SQLITE_HAS_CODEC 编译选项，旧 codec 机制整体失效；utelle 遂于 2020-08 将加密核心剥离为独立项目 sqlite3mc，wxSQLite3 自 4.6.0 起改为直接使用该实现[48]。换言之，wxSQLite3 当前的加密能力清单与 sqlite3mc 完全一致（AES-128/256-CBC、ChaCha20-Poly1305 默认、SQLCipher v1–v4、RC4、Ascon、AEGIS）[48]。选型时还需甄别一个同名陷阱：SQLiteCrypt（sqlite-crypt.com）是商业闭源软件，二进制许可 $128/平台、完整源码 $380，被 wxSQLite3 官方 README 明确标注为 "closed-source commercial solution"，不满足免费/开源要求[50][48]；官方 SQLite SEE 一次性 $2,000，同样仅作商业基准[51]。

2.4 libSQL 与 Turso

libSQL：开源 at-rest 加密的引入者，如今战略降级。 libSQL 是 Turso 团队对 SQLite 的 fork，仓库 16,991 Stars、MIT 许可，代码层面仍在推送（2026-07-24），但最新 release 停留在 libsql-server-v0.24.32（2025-02-14），server 端已 17 个月未发版；README 顶部明示"libSQL 仍在维护，但新功能正在 Turso 开发，新项目建议看 Turso"[53][62]。其加密功能于 2024-02-20 以博客《Fully Open Source Encryption for SQLite》宣布开源：page-based 加密，实现方式是直接捆绑 utelle 的 SQLite3MultipleCiphers 到 libsql-ffi[56][70]。此处存在口径冲突（交叉验证 Conflict Zone 2），须并列呈现：官方文档口径称"SQLCipher 为默认 cipher"，但 @libsql/client 的 CHANGELOG 显示 0.5.3（2024-03-06）已将默认切至 aes256cbc（wxSQLite3 AES-256-CBC 方案）——本报告按"当前默认 aes256cbc"表述并注明文档口径为历史遗留[70][74]。这一差异有实际后果：aes256cbc 无 HMAC 完整性校验，且生成的文件无法被 SQLCipher 工具链打开。已知缺陷方面，embedded replica 加密的 bug 长期未闭环：上游 issue #1122 报告 SQLCipher cipher 下副本加密不生效，2026-02 社区复现 V2 sync 路径会静默丢弃 encryption_config，导致本地副本实为明文[75][76]。

Turso Database（Rust 重写）：新势力的原生 AEAD 加密。 tursodatabase/turso 仓库 23,431 Stars、MIT 许可，最新 release v0.7.1（2026-07-22），调研前一日仍有提交，开发高度活跃；但项目整体处于 Beta，官方 FAQ 自述"not ready for production use"[53][63][79]。2025-10-07 官方博客发布原生加密，设计原则是只支持 AEAD 算法（认证加密，同时提供机密性与完整性）：AEGIS 家族（官方定位"极快"）与 NIST 标准的 AES-GCM，共 8 种 cipher（aegis256 推荐、aegis256x2/x4、aegis128l/x2/x4、aes256gcm、aes128gcm），256 位方案需 32 字节密钥[55][65][64]。实现为 per-page 加密：每次加密页面重新生成密码学安全 nonce，nonce 与认证 tag 存于页内 reserved space，主库与 WAL 文件均加密，数据库头前 100 字节不加密[55]。官方基准（batch 100、读写比 75%、AEGIS-256、15M 行）宣称读开销约 6%（5.5%）、写开销约 14%（13.5%），混合负载总时长开销仅 0.5%–2.8%；该数据无第三方复现验证，第三方索引站明确指出其 benchmark 依赖厂商自测[55][79]。成熟度方面须如实标注：加密是 experimental 特性，CLI 需 --experimental-encryption flag，官方文档将实验特性定义为"可能变更或移除、仅用于测试开发"，且无独立安全审计背书[66][79]。路线图缺口同样明确：passphrase KDF（当前必须自管原始 hex 密钥）、对既有未加密库加密、密钥轮转（rekey）均为官方 "Coming Soon"，当前不可用[64]。商业层对应 Turso Cloud 的 BYOK（Bring Your Own Key）加密，2026-02-18 起向 Pro Plan 开放，云端比本地多支持 ChaCha20-Poly1305 一族，但不支持 rekey[67][68]。

2.5 其他方案与下游生态

开源方案的落地高度依赖语言绑定与工具链，下游生态本身是选型的一部分。GUI 工具侧，SQLiteStudio 自 3.3.0 起将 DbSqliteWx 插件迁移至 sqlite3mc 1.1.4，可打开 wxSQLite3/SQLCipher/System.Data.SQLite 加密库；4.0.0 起插件正式更名 SQLite3MC，原独立 SQLCipher/System.Data 插件废弃，由 sqlite3mc 统一承接[42]。.NET 侧的路径在收窄：SQLitePCLRaw 3.0 起作者 ericsink 不再免费分发加密构建，bundle_e_sqlcipher 与 bundle_e_sqlite3mc 均已弃用，当前推荐路径为 Microsoft.Data.Sqlite.Core + utelle 官方的 SQLite3MC.PCLRaw.bundle（2.3.6，2026-07 发布），Zetetic 官方 .NET 包则仅商业授权[61][40][121][125]。Node.js 侧，better-sqlite3-multiple-ciphers（235 Stars，活跃）捆绑 sqlite3mc，PRAGMA rekey 即可加密，并可设 legacy=4 读写 SQLCipher v4 库[41]；Dart/Flutter 侧，package:sqlite3 3.4.0 起捆绑 sqlite3mc 2.3.6，并在 Web/WASM 上实验性支持加密[46]。移动端仍是 SQLCipher 的主场：Android 事实标准为官方 android-database-sqlcipher（2,800 Stars）[126]；React Native 侧 op-sqlite（1,023 Stars，活跃）内置 SQLCipher 编译开关，老的 react-native-sqlite-storage（2,823 Stars）已停更[130][132]。生产级采用案例中，Forward Email 邮件服务经 better-sqlite3-multiple-ciphers 使用 sqleet/ChaCha20-Poly1305 + WAL 逐邮箱加密 IMAP 存储[43]。

国产开源代表是腾讯 WCDB（微信团队的数据库框架）：11,618 Stars、BSD-3-Clause 许可，最新 v2.1.16（2026-03-27），维护活跃；其加密能力通过内嵌 SQLCipher 实现，可视为 SQLCipher 生态在移动端大规模落地的旁证[54]。综合来看，下游生态的流向印证了本章开篇的分层：SQLCipher 凭借十五年积累占据绑定层默认选项，sqlite3mc 以"一份实现兼容七种格式"渗透 .NET/Node/Dart/GUI 等工具链，而 Turso 的生态（@libsql/client 周下载约 104 万次[92]）则围绕其云端服务自成体系。

3. 加密与解密的运行过程

SQLite 的加密扩展不是对数据库文件的事后包装，而是钩进存储引擎内部的透明拦截：所有方案都依托 SQLite 预留的 codec（编解码器）机制，在 Pager（页式存储管理器，负责磁盘页读写与 page cache 缓存）与磁盘之间插入逐页加解密回调。本章以 SQLCipher 为参照系（SEE、sqleet、SQLite3MultipleCiphers（sqlite3mc）流程同构），沿"打开连接→密钥派生→页读写→换钥"拆解完整链路。

3.1 codec 挂载与密钥派生时序

3.1.1 打开时序：从 PRAGMA key 到首页验钥

SQLite 源码以 SQLITE_HAS_CODEC 编译开关预留加密扩展点：打开后暴露 sqlite3_key()/sqlite3_rekey() 公共 API，内部经 sqlite3CodecAttach() 挂接密钥上下文，再由内部函数 sqlite3pager_set_codec() 把回调 sqlite3Codec(data, nPageNum, nMode) 注册到 Pager 上，此后 Pager 每次读页（nMode=decrypt）或写页（nMode=encrypt）都会调用它[144][143]。由于挂接用的是内部 API，codec 无法做成运行时加载插件，加密方案只能以替换 sqlite3.c 整体构建的方式交付[1]——这也是补丁式方案随上游 API 变动而死亡的机制根源。

密钥派生采用 just-in-time（JIT） 设计：PRAGMA key 只缓存口令、不做派生计算，也永远不报错；真正的 KDF（Key Derivation Function，密钥派生函数）推迟到首次读写页面时才执行[2]。其打开时序如下：

派生环节的细节（以 SQLCipher v4 为例）：codec 从文件前 16 字节读出建库时随机写入的 salt，以 PBKDF2-HMAC-SHA512 默认 256,000 次迭代把口令派生成 32 字节加密密钥；HMAC 密钥独立于加密密钥，用 PBKDF2 仅 2 次迭代加盐掩码（盐逐字节 XOR 0x3A）派生[1][9]。每库独立随机盐保证同口令在不同库中密钥不同，可防彩虹表预计算[1]。JIT 设计还有安全收益：内存中可以只驻留口令而非派生后的 raw key——微信 4.1+（SQLCipher 4）的第三方逆向分析证实其运行时仅存 passphrase，使内存扫描直接提钥失效[145]。

3.1.2 KDF 参数对比：打开成本的分化

各主流方案在 KDF 上的取舍差异极大，直接决定"打开一个加密库需要多久"：

3.2 页级加解密数据流

3.2.1 读路径与写路径：页尾 reserved bytes 的进出

密钥派生完成后，加解密发生在每一页的进出边界。SQLite 在每页末尾预留 reserved space（头部 offset 20 记录其字节数），官方文件格式文档明确这段空间"就是为加密扩展存放每页 nonce 和/或密码学校验和而设"[139]。SQLCipher v4 每页保留 80 字节：16 字节随机 IV + 64 字节 HMAC-SHA512 tag；tag 长度随版本演进（v1 无 tag、v2/v3 为 HMAC-SHA1 的 20 字节），对应 reserved 16/48/80 字节三档，均按 AES 块对齐[9]。

读路径上，命中 page cache 的页完全绕过 codec，加解密开销只与实际触盘页数成正比——这是"索引查询开销仅 2–5%、全表扫描可放大数倍"这一性能分层的结构原因[1]。写路径上，journal/WAL 页数据与主库同密钥加密，WAL checkpoint 只是密文页搬运；但排序等瞬态临时文件不加密，需 PRAGMA temp_store = MEMORY 防明文溅落[1][146]。AEAD 系方案流程同构：sqleet 以 ChaCha20 一次性密钥（加密密钥+页号+16 字节 nonce 派生）加 Poly1305 16 字节 tag，每页共占 32 保留字节[31]；Turso 每次写页生成新 nonce，nonce+tag 同样存入 reserved space[55]。

3.2.2 文件头处理差异：互不兼容的技术根源

各方案对文件前 100 字节 header 的处理是格式互不相认的第一道分水岭。SQLite 打开文件时在加密层介入之前先读字节 16–23 以确定 page size 与 reserved bytes，故 SEE 与 sqlite3mc 非遗留模式都保留这 8 字节明文[135][32]。对照之下：SQLCipher 默认用 16 字节 KDF 盐直接覆盖 offset 0–15 的 magic 字符串，整文件呈白噪声，普通工具连"这是 SQLite 文件"都无法识别（v4 起可用 cipher_plaintext_header_size 保留明文头，但盐需另行管理）[1][34]；Turso 最激进，前 100 字节 header 整体明文[55]。"盐放不放头部、头留多少明文"的格式决策叠加 KDF 参数与页布局差异，构成第 4 章将展开的方案间互不兼容的技术根源。

3.3 密钥错误行为与 rekey 机制

由于 JIT 派生，错误密钥不会在开库时暴露：PRAGMA key 永远"成功"，直到首次读页 HMAC 校验失败才报错——且报的不是认证错误，而是笼统的 "file is encrypted or is not a database"（SQLITE_NOTADB, code 26）[2][140]。密钥错误、cipher 版本不匹配（v2 打 v4）、方案不匹配（sqleet 打 SQLCipher）全都收敛为同一个错误码，应用层必须主动用 SELECT count(*) FROM sqlite_master 之类的探针验钥[2][143]；cipher_compatibility、kdf_iter 等非默认参数也必须在 PRAGMA key 之后、首个实际操作之前设置，且非默认值建库后每次打开都要重设[2]。

换钥（rekey）的本质是全库逐页重加密：先用旧钥解密全部页面，用新口令重新派生密钥，逐页加密回写并更新头部 salt[143][57]。实现路径各有不同：sqleet 的 sqlite3_rekey() 内部直接跑 VACUUM 完成全页重写[57]；SEE 以 .rekey OLD NEW NEW 配合 VACUUM 保证每页 nonce 安全[135]；sqlite3mc 借助修改版 VACUUM 过程实现原地（in-place）换 cipher——先以 PRAGMA cipher/legacy 选定目标方案再 PRAGMA rekey，无需像 SQLCipher 的 sqlcipher_export() 那样 ATTACH 后整库复制，这是其作为"多格式逃生舱"的运行时基础[38]，v2.4.0 起还支持 WAL 模式下 rekey，代价是保留旧 key salt 的轻微安全折损[28]。Turso 目前完全没有 rekey 能力，换钥只能导出后重建[64]。关闭连接时 codec 上下文销毁并清零密钥与明文缓冲区（SQLCipher v4 起默认全量内存擦除），但所有方案都明示：页进入内存后即为明文，加密只保护静态数据[4][135]。

4. 与官方 SQLite 的兼容性

加密方案在 SQL 层保持 SQLite 语义不变——同一套 SQL、同一批 PRAGMA 照常可用；真正的不兼容发生在三个层面：磁盘文件格式、运行时特性的边界行为、以及围绕数据库文件的工具链。第 3 章已指出，文件头处理（magic 是否被盐覆盖、字节 16–23 是否明文）与页尾 reserved bytes 布局的差异是格式互不兼容的技术根源，本章据此展开三个层面的兼容性清单。

4.1 文件格式兼容性

4.1.1 加密库对普通 sqlite3 一律拒绝打开，方案之间互不相通

任何一个加密库文件交给官方 sqlite3 CLI 或不了解对应 cipher 的工具，结果都是同一个错误："file is encrypted or is not a database"（SQLITE_NOTADB，code 26）。SQLCipher 官方设计文档给出了完整实演：加密库 hexdump 呈白噪声，普通 sqlite3 对其执行任何查询立即报此错；Android 生态中同一问题表现为 SQLiteException: file is not a database (code 26)[1][140]。更棘手的是，这个错误把多种完全不同的成因折叠在一起——密钥错误、SQLCipher 版本不匹配（如 v2 客户端打 v4 库）、方案不匹配（sqleet 打 SQLCipher 库）全都报 SQLITE_NOTADB，排查时只能逐项对齐 cipher 方案、KDF 迭代数、page size 与 legacy 参数[2]。

方案之间的格式隔离是双向的。sqleet 与 SQLCipher 在算法（ChaCha20-Poly1305 对 AES-256-CBC）、KDF（PBKDF2-HMAC-SHA256/12,345 迭代对 SHA512/256,000 迭代）与 header 布局上均不同，文件互不可读[57][1]；即便在 SQLCipher 内部，v4（2018-11）将默认 page size 由 1024 改为 4096、KDF 迭代由 64,000 提至 256,000、KDF/HMAC 算法由 SHA1 换为 SHA512，默认配置打不开 v1–v3 的库，须借助 PRAGMA cipher_compatibility = N 读旧库或 PRAGMA cipher_migrate 原地升级[4][101]。需要区分"可识别"与"可打开"：SEE 保留文件头字节 16–23 明文、Turso 保留前 100 字节 header 整体明文，因此这两类文件能被工具识别为 SQLite 格式（magic 可见），但没有密钥与对应引擎照样读不出任何数据[135][55]。

4.1.2 SQLite3MultipleCiphers legacy 模式：唯一的"格式逃生舱"

SQLite3MultipleCiphers（下称 sqlite3mc）在单一库中实现了 6 套以上 cipher scheme——wxSQLite3 AES-128/256-CBC、sqleet ChaCha20、SQLCipher v1–v4、System.Data.SQLite RC4、Ascon、AEGIS[30]。通过 URI 或 PRAGMA 显式指定 cipher 与 legacy 参数（如 cipher=sqlcipher&legacy=4 读 SQLCipher v4 文件、cipher=chacha20&legacy=1 读原版 sqleet 文件），它可以读写其他方案的原生文件，并借助修改版 VACUUM 过程原地完成加密、换 cipher 或解密，无需像 SQLCipher 的 sqlcipher_export() 那样整库复制[32][38]。这使其成为目前已知唯一具备跨格式读取能力的实现，即"格式逃生舱"。但有一个易踩的反向陷阱：sqlite3mc 默认的非 legacy 模式保留字节 16–23 明文，写出的文件与原版 sqleet/SQLCipher 并不兼容，必须显式设置 legacy=1 才能产出互通文件[32]。libSQL 的 cipher=sqlcipher 方案底层复用同一 SQLCipher cipher scheme，理论上其加密文件可被 SQLCipher v4 工具链打开，但官方文档未作承诺，也未找到第三方验证，此处标记为数据缺口[9][71]。

4.2 运行时特性兼容

加密对 SQLite 运行时特性的支持并不均一，逐项核对结果如下。WAL 与 journal：SQLCipher、SEE、sqlite3mc、Turso 一致地对 WAL 与 rollback journal 中的页数据用数据库同一密钥加密，VACUUM 产生的 journal 同样加密；WAL 模式下备份须同时保留主库与 -wal 文件，两者均为敏感密文[1][146]。sqlite3mc 提供 PRAGMA mc_legacy_wal 兼容 1.2.5 及之前版本的旧 WAL 加密模式，且 v2.4.0（2026-07-25）起支持在 WAL 模式下执行 rekey——代价是保留旧 key salt，属于轻微安全折损[36][28]。临时文件：排序、索引等瞬态 temp 文件不加密，必须编译期 --enable-tempstore=yes（SQLITE_TEMP_STORE=2）加运行期每连接 PRAGMA temp_store = MEMORY 双保险，否则明文会溅落磁盘[1][146]。ATTACH 混合库：SQLCipher 自初版即支持同一连接挂载加密库与明文库，ATTACH 时以 KEY '' 表示目标库不加密；sqlcipher_export() 负责明文与加密双向互转，复制 schema、触发器、虚拟表与全部数据，但不复制 user_version 与 auto_vacuum 设置[136]。Backup API：SQLCipher 4.1.0 起对加密库显式禁用 online backup API（初始化即报错），4.3.0 放宽为仅允许加密→加密的备份[4]。page size 匹配：sqleet 因 header 全加密无法从文件读出 page size，非默认 page size 的库即使密钥正确也打不开；SQLCipher 非默认 cipher_page_size 的库每次打开都须重设该参数[57][2]。Turso 的缺口：其原生加密暂不支持口令 KDF、既有明文库加密、rekey 与 ATTACH，均在路线图上[55]。

4.3 工具链兼容

GUI 工具必须内置对应 cipher 支持才能打开加密库。SQLiteStudio 自 3.3.0（2021）起将加密插件迁移至 sqlite3mc，4.0.0 起以 SQLite3MC 插件统一承接 wxSQLite3/SQLCipher/System.Data.SQLite 三类格式，原独立 SQLCipher 插件废弃[42]；DB Browser for SQLite 内置 SQLCipher 支持，与 sqlite3mc legacy 模式产出的 SQLCipher 格式文件可直接互通[41]。Turso 加密为自有 AEAD 格式，官方各 SDK 文档统一声明加密库"必须用 Turso Database 引擎打开"，目前无任何第三方工具生态[64][72]。明文库与加密库之间的离线互转，标准路径是 ATTACH 加 sqlcipher_export()，或 sqlite3mc 的原地 rekey（见 4.2 节），不存在跨方案的格式直转工具[136][38]。

5. 性能对比

加密对 SQLite 性能的影响无法用单一百分比概括。调研发现，所有量化数据都可以归入两条相互独立的性能轴：打开成本（连接建立时的一次性 KDF 计算）与稳态成本（运行期每页加解密）。混淆这两条轴是性能评估中最常见的错误来源——"加密慢 X%"这类脱离连接模型与查询形态的数字几乎没有意义。本章先建立分析框架，再逐方案呈现实测数据，包括存在矛盾口径的数据点。

5.1 两个独立的性能轴

5.1.1 KDF 打开成本：一次性、与连接频率成正比

SQLCipher 4.x 默认执行 256,000 次 PBKDF2-HMAC-SHA512 迭代（等效约 512,000 次 SHA512 运算），该计算在每次打开数据库连接时完整执行一次，属于刻意设计的高成本（抗暴力破解）[156]。第三方中文博客在普通手机 CPU 上的实测给出了近似线性的验证时间：6,000 迭代约 5ms、64,000 约 30ms、100,000 约 50ms、500,000 约 220ms；按线性外推，默认 256,000 迭代对应约 100–120ms 的打开延迟[149]。腾讯 WCDB 的 Android benchmark 提供了端到端佐证：Nexus 5X（arm64）上明文库建库耗时 49ms，而 SQLCipher 加密库（含 KDF 与加密建库）为 303ms[153]。该来源未注明具体机型与 SQLCipher 版本，且文中将默认迭代数误写为 64,000，故置信度标为中低，但其量级与 PBKDF2 线性特性一致[149]。

对照之下，Turso Database 原生加密完全不执行 KDF：用户直接提供 32 字节 hex key，连接打开即就绪，不存在 PBKDF2 打开延迟[55][152]。sqleet 则走另一条路线——PBKDF2-HMAC-SHA256 仅 12,345 迭代，打开成本远低于 SQLCipher 默认值，但抗暴力破解能力相应削弱[148]。由此得出的操作结论是：高频短连接场景（serverless、CLI 工具）中 KDF 主导延迟，SQLCipher 官方性能文档因此明确要求"不要反复打开关闭连接"[8]；而长连接服务端的稳态吞吐才取决于下述页开销。

5.1.2 稳态页开销：与访问页数成正比

运行期开销的机制是每页独立加解密（SQLCipher 对每 4KiB 页计算 AES-256-CBC + HMAC-SHA512；Turso 对每页用唯一 nonce 做 AEGIS-256），因此开销与一次查询触及的页数成正比[55]。索引点查只解密少量页，实测开销可低至 2–5%；而非索引全表扫描需解密全部页，第三方实测极端值达到 +496%[147]。这正是官方宣称"5–15%"与实测极端值相差两个数量级的根源：两者描述的是不同的查询形态。

算法选型由硬件指令集决定。OpenSSL speed 实测数据（Intel i7 七代）显示：有 AES-NI 硬件加速时 AES-256-GCM 吞吐约 3.8GB/s，无硬件加速的软件 AES 仅约 134MB/s（约 28 倍差距）；ChaCha20-Poly1305 软件实现约 2GB/s，在无 AES 指令集的低端 ARM 与嵌入式平台上显著优于软件 AES[155]。这是 sqleet 与 SQLite3MultipleCiphers 默认选择 ChaCha20 的核心理由[148][29]；反之 SQLCipher 4 在 iOS 上凭借 4K 页与硬件加速获得 2 倍以上提升[156]。

5.3 调优手段

针对两条性能轴，调优手段也分两类。压缩打开成本：使用 RAW key（预先派生好的 256 位密钥）可完全跳过 PBKDF2[8]；或将 PRAGMA kdf_iter 从 256,000 降至 64,000，官方称可将密钥派生耗时减少为四分之一[8][2]——但须明确这是以抗暴力破解能力换延迟，降低迭代数的定制部署已有成熟破解工具链的先例。工程上更稳妥的做法是连接复用，避免为每次操作重开连接[8]。压缩稳态成本：用事务包裹批量写入（WCDB 实测可消除几乎全部加密差距）[153]；启用 WAL 模式使加解密与 I/O 并行[153]；SQLCipher 4 默认 page_size 已从 1024 提至 4096，更大的页摊薄每页 IV/HMAC 的固定开销，服务器场景可进一步调大[156][2]。其余可选杠杆包括关闭 cipher_use_hmac（放弃完整性校验）与 secure_delete[8]，以及保持 cipher_memory_security 默认关闭——实测开启后 insert 开销从 +2.3% 升至 +27%[147]。上述每一项调优都同时是安全降级决策，应纳入威胁模型评估而非纯性能取舍。

6. Drizzle ORM 接入实战

前面章节的调研指向一个反直觉的结论：加密 SQLite 接入 Drizzle 的真实成本不在 ORM 层，而在 drizzle-kit 工具链。三条可行路径（libsql 原生 encryptionKey、better-sqlite3-multiple-ciphers 顶替、sqlite-proxy）在运行时对 Drizzle 完全透明——查询构造、关系加载、类型推导与常规 SQLite 用法零差别；断裂的是所有需要真实连库的 CLI 命令（push/migrate/studio/pull），因为 drizzle.config.ts 的 dbCredentials 没有 encryptionKey 注入点[166]。因此本章的结构是：先给出三条路径的完整接入配置（6.1–6.3），再集中讨论与常规用法的差异点与工具链绕行方案（6.4）。

三条路径的共同点是"Drizzle 层的代码不需要为加密改任何一个字"，差异全部发生在连接建立与 schema 迁移两个环节。选择逻辑很直接：有 Node 运行时且不介意 libsql 私有加密格式选 A；需要与 SQLCipher 生态（DB Browser、移动端 SDK）互通选 B；进程里没有原生 SQLite 可用（WebView、移动端 JS 层）只能选 C。路径 A 与 B 的分界还涉及格式锁定问题——libSQL 加密的文件无法用标准 SQLite 读取，反之亦然[71]，这一锁定成本在第 7 章选型决策中展开。

6.1 路径 A：libsql 驱动原生加密

Drizzle 官方文档明确将 "encryption at rest" 列为 libsql 驱动相对 better-sqlite3 与 node:sqlite 的原生优势，且 connection 对象允许传入任意 libsql 连接选项[90]。@libsql/client 本身维护活跃：最新版 0.17.3（2026-04 发布），npm 周下载约 104 万次[92]。运行时接入仅需在 createClient 时多传一个参数：

// src/db/index.ts —— 路径 A 运行时接入，与常规用法的唯一区别是 encryptionKey
import { createClient } from '@libsql/client';
import { drizzle } from 'drizzle-orm/libsql';
import * as schema from './schema';

export const client = createClient({
  url: `file:${process.env.DB_FILE_NAME}`,   // 本地文件库；远程 libsql:// 亦可
  encryptionKey: process.env.ENCRYPTION_KEY, // ← 加密配置的全部增量
});

// 之后的所有 Drizzle 用法（select/insert/事务/关系查询）与常规 SQLite 完全一致
export const db = drizzle(client, { schema });

也可以把 key 直接放进连接串：file:x.db?encryptionKey=...（Astro DB 文档确认了这一形式）[171]。加密是页级（page-level）而非整文件解密[70]，加密后的文件呈现为随机字节，任何标准 SQLite 工具都无法读取[71]。

两个必须知道的上游事实。其一，默认 cipher 的口径存在时间性冲突：libSQL 官方文档称默认 cipher 为 SQLCipher，但 @libsql/client 自 2024-03 起已将默认切换为 aes256cbc[74]；按当前行为表述即"现默认 aes256cbc，可选 SQLCipher 兼容模式"，打开旧库时务必显式指定 cipher。其二，嵌入式副本（embedded replica，配置 syncUrl）模式下加密会被静默丢弃——V2 sync 协议路径丢失 encryption_config，本地副本文件实际是明文，上游 issue（libsql#1122、tauri-plugin-libsql#1）有完整根因分析，截至调研时未修复[76][158]。凡涉及 sync 的部署必须先实测副本文件是否加密。

6.2 路径 B：better-sqlite3-multiple-ciphers 顶替

better-sqlite3-multiple-ciphers 是 better-sqlite3 的活跃 fork，内置 SQLite3MultipleCiphers，版本号与上游一一对应（12.11.1 对应 better-sqlite3 12.11.1 + SQLite 3.53.2），API 完全一致并自带类型声明[157][82]。其生态体量可观：npm 周下载约 65,709 次，Snyk 维护健康度评级为 "Healthy"[83]。接入的关键技巧是 npm alias——包名仍叫 better-sqlite3，使得 drizzle-orm/better-sqlite3 内部的 import Database from 'better-sqlite3' 和全部类型声明无缝命中 fork，无需任何类型 cast。这一模式有生产级实证：开源 POS 项目 puntovivo（Electron 42 + Fastify + tRPC 11）正是用 alias 完成替换[177]。该 fork 中文社区也确认它是 better-sqlite3-sqlcipher（停留在 v5.4.3、已无法在现代 Node 编译）的事实继任者[163]。部署侧的主要成本是原生模块分发：官方为 Windows/Linux/macOS（含 Alpine、arm64）提供 Node v22/v24/v26 与 Electron v29–v42 的预编译二进制，Node v20 自 v12.10.0 起不再提供预编译，需回退到源码编译[82]：

{
  "dependencies": {
    "better-sqlite3": "npm:better-sqlite3-multiple-ciphers@^12.11.1",
    "drizzle-orm": "^0.45.2"
  }
}

连接建立时的 PRAGMA 顺序是这条路径最容易踩的坑。fork 的默认 cipher 是 sqleet 而非 SQLCipher，要打开/创建 SQLCipher 4 兼容格式的库，必须先发 cipher 与 legacy=4，再发 key，且全部 PRAGMA 必须在第一条 SQL 语句之前完成[34]：

// src/db/connection.ts —— 路径 B：alias 后的连接与 key 注入（puntovivo 生产同款）[^178^]
import Database from 'better-sqlite3'; // 实际解析到 better-sqlite3-multiple-ciphers
import { drizzle } from 'drizzle-orm/better-sqlite3';
import { migrate } from 'drizzle-orm/better-sqlite3/migrator';
import * as schema from './schema';

const sqlite = new Database('./data/app.db');

// ★ 顺序不可乱：cipher → legacy → key → 其他 PRAGMA；必须在任何 SELECT/DDL 之前
sqlite.pragma("cipher = 'sqlcipher'");
sqlite.pragma('legacy = 4');
sqlite.pragma(`key = "x'${process.env.DB_KEY_HEX}'"`); // 32 字节 raw key 的 64 位 hex

sqlite.pragma('journal_mode = WAL');

export const db = drizzle(sqlite, { schema }); // 常规 drizzle 用法零差别

// 迁移在运行时执行（drizzle-kit migrate 对加密库不可用，见 6.4）
// 注意：迁移前在连接级关闭 FK，绕开 drizzle 事务包裹致 PRAGMA 失效的坑（issue #5782）[^170^]
sqlite.pragma('foreign_keys = OFF');
try {
  migrate(db, { migrationsFolder: './drizzle' });
} finally {
  sqlite.pragma('foreign_keys = ON');
}

"只传 key 不传 cipher"的典型后果是首次读写时报 file is not a database——TypeORM 同名 issue（#8475）从反面验证了这一顺序约束[169]。另有两个行为细节：PRAGMA key 即使密码错误也返回 ok，错误要到首次读写才暴露，验证方式是立刻执行一次 SELECT * FROM sqlite_master[34]；:memory: 内存库不支持 key，fork 会直接抛 Setting key not supported for in-memory or temporary databases，意味着依赖内存库的单元测试需要改造[178]。

6.3 路径 C：sqlite-proxy（Tauri / 移动端）

Drizzle Proxy 是官方支持的"自带驱动通信层"模式：drizzle(async (sql, params, method) => {...})，callback 把 Drizzle 生成的 SQL 发到任意后端（Tauri command、HTTP 服务），按 {rows: string[][]} 约定返回；v0.29.5 起 sqlite-proxy 支持 batch 回调与关系查询[173][174]。加密对 Drizzle 完全透明——key 与解密发生在 proxy 背后的驱动里，这使它成为 WebView/移动端（无 Node 运行时）的唯一解。现成方案是 tauri-plugin-libsql，提供加密版 proxy 工厂与浏览器安全的迁移器[99][158]：

// src/db/index.ts —— 路径 C：Tauri 环境下的 sqlite-proxy + 加密 + 构建期内联迁移
import { drizzle } from 'drizzle-orm/sqlite-proxy';
import { createDrizzleProxyWithEncryption, migrate } from 'tauri-plugin-libsql-api';
import * as schema from './schema';

// WebView 里没有 fs，标准 sqlite-proxy/migrator 读不了 .sql 文件；
// 用 Vite import.meta.glob 在构建期把迁移 SQL 内联进 bundle，由插件的 migrate() 按序应用
const migrations = import.meta.glob<string>('./drizzle/*.sql', {
  eager: true, query: '?raw', import: 'default',
});
await migrate('sqlite:encrypted.db', migrations);

export const db = drizzle(
  createDrizzleProxyWithEncryption({
    path: 'sqlite:encrypted.db',
    encryption: { cipher: 'aes256cbc', key: myKey32Bytes }, // Uint8Array，必须 32 字节
  }),
  { schema },
);

const users = await db.select().from(schema.users); // 常规 drizzle 用法零差别

该插件 README 醒目警告：embedded replica 模式同样踩 6.1 所述的上游加密静默失效 bug[158][76]。若自写 proxy callback（例如 Rust 侧 sqlx + SQLCipher，连接建立时注入 pragma("key", ...)），需注意一个重大限制：db.transaction(async tx => {...}) 不可用——proxy 把事务内每条语句作为独立查询发送，后端无法感知事务上下文；解法是用 db.batch()（在单事务上下文中执行）或为复杂事务写专用 Tauri command[100]。kunkun.sh 给出了基于 @tauri-apps/plugin-sql 的自写 callback 完整实现（按 isSelectQuery 分流、按 method 组装返回值），可原样套到任何加密后端[165]。移动端变体同理：expo-sqlite 开库后立即 PRAGMA key（Drizzle 是其官方点名集成）[161]；op-sqlite 用 sqlcipher: true 编译开关，drizzle-orm/op-sqlite 驱动照常使用[176]。Capacitor 生态的 @capacitor-community/sqlite 则在原生端内置 SQLCipher、Electron 端直接复用路径 B 的 better-sqlite3-multiple-ciphers，官方文档同样列出 Drizzle 集成方式[164]——可见路径 C 的"proxy 背后接什么驱动"问题，在各平台上都已有现成答案。

还需要提示一个跨路径的迁移细节：drizzle 官方 sqlite-proxy migrator 在运行时通过 Node fs 读取 .sql 文件，这一假设在 WebView/移动端全部失效，因此凡走路径 C 的项目都必须采用构建期内联 SQL 的方案（如上文 import.meta.glob），这是与常规 SQLite 迁移流程的隐性差异之一[158]。

6.4 与常规 SQLite 的使用差异

6.4.1 drizzle-kit 工具链断裂与迁移工作流改造

这是加密接入与常规用法最大、也最容易被低估的差异。drizzle-kit generate 是纯静态分析 schema.ts 生成 SQL，不连库，因此永远可用；但 push / migrate / pull（introspect）/ studio 对加密库全部报 SQLITE_NOTADB，因为 dbCredentials 没有 encryptionKey 参数，drizzle-kit 内部以普通驱动打开文件，读到的是密文[166]。对应 feature request drizzle-team/drizzle-orm#3198 于 2024-10 提出，截至 2026-05-16 仍为 open（16 个 👍，最近一条评论仍在催更）；团队成员 2025-08 的批量回复表明工作重心在 drizzle-kit 重写与 v1，该需求未被单独认领[166]。实战中的一个典型陷阱是：文档没有 encryptionKey，有人误以为参数名错误改成 authToken，结果"不报错"了——实际是加密被静默禁用，库文件以明文落盘[102]。

社区共识的绕行方案是"生成与执行分离"：generate 离线生成 SQL，应用启动时用运行时 migrator（复用已带 key 的连接）执行迁移：

// scripts/migrate.ts —— 用带 encryptionKey 的运行时 client 替代 drizzle-kit migrate
import { createClient } from '@libsql/client';
import { drizzle } from 'drizzle-orm/libsql';
import { migrate } from 'drizzle-orm/libsql/migrator';
import 'dotenv/config';

const client = createClient({
  url: `file:${process.env.DB_FILE_NAME}`,
  encryptionKey: process.env.ENCRYPTION_KEY,
});
const db = drizzle(client);

await migrate(db, { migrationsFolder: './drizzle' }); // 由 drizzle-kit generate 离线生成
console.log('migrations applied');
flowchart TD A["修改 schema.ts"] --> B["drizzle-kit generate（纯静态分析，不连库）"] B --> C["drizzle/ 目录生成 SQL 迁移文件"] C --> D{"如何应用迁移？"} D -->|"drizzle-kit push / migrate"| E["失败：SQLITE_NOTADB，dbCredentials 无 encryptionKey 注入点（issue #3198 open）"] D -->|"运行时 migrator（推荐）"| F["tsx scripts/migrate.ts 或应用启动时 migrate()"] F --> G["复用带 key 的连接，迁移正常落盘"] E --> H["pull / studio 同样不可用；临时解法是先解密出明文副本再操作"]

这一工作流改造是"Drizzle + 加密 SQLite"真正的接入成本：CI 里跑 generate，应用启动序列里跑 migrate（puntovivo 即把迁移作为启动时的唯一 schema 路径）[177][178]。它同时兼容另一个非加密特有的坑——drizzle-kit 在 Electron 环境下会因 ABI 不匹配报 NODE_MODULE_VERSION 错误（drizzle-kit 用宿主 Node 的 better-sqlite3 构建），生成与执行分离恰好一并绕开[175]。两个附带注意事项：drizzle-kit 使用 libsql dialect 时要求本地安装 @libsql/client 包，否则报 "please install required packages: '@libsql/client'"[167]；dialect: 'turso' 时 url/authToken 为必填校验，本地 file: URL 可不带 authToken[168]。

7. 选型决策框架与建议

前文六章给出了方案全景、原理、格式兼容性、性能开销与 Drizzle 接入路径，本章不再重复这些数据，只做决策综合：先用三条否决线排除"不该做文件级加密"的情形，再按数据位置→合规级别→格式互通需求收敛到具体方案。

7.1 三条否决线先行

否决线一：密钥只能硬编码。 文件级加密的全部安全强度系于密钥，而硬编码在客户端二进制中的密钥可从 APK/可执行文件直接提取，用 Frida hook 关闭加密也只是"有趣的逆向挑战"级别的工作量[184][189]。Signal 模式之所以成立，是因为密钥存放在 Android Keystore/iOS Keychain 中、由操作系统信任链保护；即便如此，root 设备上仍可通过内存 dump 取到明文密钥[185]。若目标平台没有任何可用的 Keystore/KMS，文件级加密退化为混淆，应停止选型、先解决密钥管理。

否决线二：服务端已有 FDE 且威胁模型是在线攻击。 全盘加密（FDE）与数据库文件加密都只保护"介质离线"场景；对已拿到系统访问权的在线攻击者，运行态的加密文件"might as well be plaintext"，再叠一层数据库加密属于 security theater[196][197]。机房/云盘已有 FDE 或云 KMS 时，"enable Full Disk Encryption and call it a day"是合理终点[196]。

否决线三：仅个别字段敏感。 整库加密做不到颗粒度，也让其余本可查询的数据一并不可检索。真正匹配"只有 PII/支付列敏感"的方案是应用层字段级加密、密钥外置 KMS/HSM，连 DBA 也无法解密；WorkOS 引述的 Forrester 数据称采用应用层加密的企业内部人泄露事件减少 78%（厂商立场数据，仅供参考）[198][199]。折中选项是 SQLCipher 商业版独占的 Value Level Encryption（库内部分加密），但其 $999/应用/年起的订阅门槛需计入成本[20][179]。

表中有三点值得展开。移动端推荐强度最高，因为信任链最完整：密钥有 OS 级硬件/TEE 背书，SQLCipher 有 Signal、Salesforce SmartStore 等大规模生产先例[185][22]，体积与性能成本均已量化。桌面端的短板在密钥——没有统一的 Keystore 抽象，密钥若随安装包分发即触发否决线一。Go 后端的排序反映生态现实而非方案优劣：mattn 路径成熟但要管 cgo 与系统库；go-libsql 一行接入（243★，绑定 Turso 生态）[108]；ncruces adiantum VFS 是唯一的 cgo-free 选项，但其 README 明确声明"不防篡改"、确定性加密下多快照可区分块变化，只适合低威胁场景[110]。多租户一行中的副本加密 bug 是本表唯一的实测红线：它是上游已确认、社区复现的问题，不是理论风险[76]。

7.3 2026 年生产选型结论

开源格局已收敛为"一超一强一新"三层：SQLCipher（7,213★，移动端事实标准，BSD 社区版＋三档商业版）[52][179]、SQLite3MultipleCiphers（661★，但下游覆盖最广，被 LumoSQL 知识库称为"截至 2026 年最活跃维护的开源 SQLite 加密方案"）[122][182]、Turso（23,431★，但加密仍为 experimental、无第三方工具链）[53][66]。据此，2026 年的成熟生产路径只有两条：SQLCipher 系与 sqlite3mc 系。两者的选择不是优劣题而是生态题：要 FIPS 140-3 验证（注意 140-2 证书 2026-09-21 全部转 Historical，新采购须按 140-3 评估）、商业支持或移动端先例，选 SQLCipher[5][206]；要格式逃生舱——sqlite3mc 的 legacy 模式可读写 SQLCipher v1–v4 与 sqleet 文件，是唯一不被单一格式锁死的方案——或免费多 cipher 组合，选 sqlite3mc[32]。Turso 加密适合新项目试水：性能与工程体验领先，但必须接受"文件只能被 Turso 引擎打开"的锁定与 experimental 状态，核心生产数据建议等其加密标记转正、第三方工具链出现后再迁入[66]。预算充足且要求官方背书的嵌入式场景，SEE（约 $2,000 一次性永久授权，HN 有 13 年无故障使用反馈）仍是合规捷径[191]。

8. 攻击向量与明文生命周期

第 3 章已确立页级加密模型的基本事实：内存恒明文、落盘恒密文；第 7 章的推荐架构（bun compile 单文件分发 + better-sqlite3-multiple-ciphers + UKey 启动时注入 raw 32 字节 key）把密钥移出了二进制，但只堵住"拷文件 + 逆向提 key"一条路径。本章回答两个问题：除离线拷贝外还有哪些现实攻击面；明文与密钥在磁盘、内存各处停留多久、能被什么机制清除。基线判断：SQLCipher v4/sqlite3mc 的磁盘侧设计（AES-256-CBC、每页独立随机 IV、每页 HMAC-SHA512、文件含 WAL 呈白噪声）无已知弱点，raw key 模式跳过 PBKDF2[1][34]，"离线拷文件且无密钥"不可破，攻击面全部转移到运行时、旁路副本、主机与交付链路三类。

表中三条规律值得注意。其一，威胁排序与加密强度无关：排名最高的两类（内存读取、core dump）完全绕开密码学、直接读取解密后的产物，是"内存恒明文"架构属性的必然推论。其二，旁路类向量（导出通道、temp、日志）攻击前提最低——不需要 root 和调试器，任何能执行 SQL 或读日志的路径即可触发，反而最可能首先被利用。其三，UKey 交互层概率最低但不可消除：raw key 必须离开硬件进入主机内存，是架构的固有暴露窗口而非配置缺陷。

8.1.1 运行时攻击面

运行时内存读取门槛极低：gdb -p <pid> 附加后 dump，或遍历 /proc/<pid>/maps 逐段转储再 strings 检索。权限由 yama ptrace_scope 决定：=0 同 uid 即可附加，多数发行版默认 =1（仅限父进程），=2 需 CAP_SYS_PTRACE，=3 完全禁止[217]；Linux 3.3 起读 /proc/<pid>/mem 与 ptrace 权限等价[218]。由此产生一个高价值联动：prctl(PR_SET_DUMPABLE, 0) 不仅禁 core dump，还让同 uid 非特权进程无法读 /proc/<pid>/mem，一次调用封堵两条路径，应在启动早期执行[219][220]。root 或持 CAP_SYS_PTRACE 者可绕过一切用户态防护，不可防，只能纳入"主机沦陷即失败"假设[217][218]。容器环境有两处反直觉差异：默认不授 CAP_SYS_PTRACE，内存读取面反而收窄[221]；但 coredump 内核接口不做 namespace 隔离，容器内进程的 dump 落到宿主机，且容器可自设 ulimit -c——宿主禁了 coredump ≠ 容器内不产生[223][224]。core dump 封堵需多层叠加：进程 PR_SET_DUMPABLE=0、rlimit（systemd 服务需另配 DefaultLimitCORE=0）、sysctl、systemd-coredump Storage=none、容器 --ulimit core=0[222][225]；apport、ABRT 及 Node 的 --report-on-fatalerror/heapsnapshot 可能绕开部分层[224]。

8.1.2 数据旁路

最危险的旁路是合法导出通道：官方文档明确演示 ATTACH DATABASE 'plaintext.db' AS plaintext KEY ''; SELECT sqlcipher_export('plaintext'); 即生成全量明文副本[136]，VACUUM INTO 同样能把整库写到任意路径[216]——任何能执行 SQL 的路径（注入、调试接口、被 hook 的连接）都等价于"整库明文带走"。缓解在连接层：SQLITE_DBCONFIG_ENABLE_ATTACH 置 0 或 authorizer 拒绝 ATTACH/DETACH 并审计 VACUUM INTO；备份侧 SQLCipher 4.1.0 起禁止对加密库用在线备份 API[233][234]。第二处是 temp 文件：排序、瞬时索引、物化子查询的临时文件不经 codec、内容为明文[235][146]，官方建议是编译期 SQLITE_TEMP_STORE=2/3、每连接 PRAGMA temp_store = MEMORY，代价是大排序内存无界、可能 OOM[29][236]。第三处是日志：SQL 文本、绑定参数、异常堆栈进入日志或 APM 即成长期留存的明文副本，OWASP ASVS V3.1.1 类规范要求敏感数据不进日志[237]；SQLCipher CLI 编译 readline 时把 PRAGMA key 从历史剔除，属同一思路[238]。

8.1.3 环境与分发层

swap 与休眠是内存明文的被动落盘通道：密钥与明文页可被换出且进程退出后残留；休眠（S4）把全部 RAM（含 mlock 页）写入休眠镜像——mlock 只防常规换出且按页对齐，这正是 sqlite3mc 官方拒绝"锁定所有分配"的理由[226][227][34]。可靠解法在 OS 层：禁/加密 swap、vm.swappiness=1、禁休眠[225][228]。分发链路上，bun build --compile 内嵌 JS 源码可被现成工具提取，混淆只提高成本，藏在代码里的密钥派生逻辑应视为公开——本场景密钥在 UKey 中，方向正确[232]；但 JS 层打包不等于原生代码全静态链接，LD_PRELOAD 可同名覆盖 sqlite3_key、OpenSSL EVP 等符号截取密钥（/etc/ld.so.preload 是 MITRE ATT&CK T1574.006 持久化手段），静态链接可免疫，需核实 OpenSSL/sqlite3mc 是否静态进二进制[229][230]。Frida 可按导出符号或静态分析偏移 hook 任意原生函数 dump 出 raw key，反检测是"通常攻击者能赢"的猫鼠游戏[231]。预编译 .node 与 npm 依赖链被替换可在 codec 内植马，Node policy 完整性校验曾存在绕过漏洞（CVE-2023-38552），现实组合是锁定依赖 + 私有 registry + 代码签名[239][240]。UKey 交互层：PIN 爆破依赖片上重试计数器，TPM 同类机制示例为"立即 32 次、之后每 2 小时 1 次"，4 位 PIN 全枚举需两年以上，需确认所用 UKey 的锁定策略[241]；raw key 导出瞬间必然以明文经过主机内存与总线，是全架构最脆弱一刻，支持卡内运算或包裹导出的 UKey 应优先；PKCS#11 的 C_Login PIN 以参数进入进程地址空间、可被 hook[243]。

8.2.1 磁盘侧

主库是密文，但已删除数据残留是第一处陷阱：secure_delete=off 时 freelist 页与空闲块中的已删记录可用取证工具恢复[244][245]。secure_delete 默认口径在三处来源间存在差异，须并列呈现：标准 SQLite 默认 OFF（除非编译 SQLITE_SECURE_DELETE）[213][214]；SQLCipher 官方构建按惯例默认 ON[251]；sqlite3mc 取决于发行构建，属数据缺口，必须以 PRAGMA secure_delete; 实测确认。即便开启，WAL 模式下也要等 checkpoint 才零化主库，旧内容在截断前仍可恢复——DFRWS 2019 实验证明 secure_delete + WAL 下全部已删记录仍可从 WAL 帧历史完整恢复[248][215]；FAST 档只清 B-tree 页不清 freelist，官方自承"并不真正安全"，且均不覆盖 FTS 影子表[213][215]。VACUUM 重建库文件、仅拷存活页，官方明确"清除所有已删内容痕迹"，代价约 2 倍磁盘空间与全程写锁[216]。WAL 帧与主库同 key 加密（首帧前 16 字节盐为明文头），rollback journal 同为密文且事务结束即删，更利于安全删除[246][247][215]。介质物理层是第二处陷阱：SSD 磨损均衡使"已覆盖"数据以残影长期存在，覆写不可靠、TRIM 回收时间不确定；NIST SP 800-88 认定对 SSD 可靠的只有 Secure Erase、加密擦除（销毁密钥）与物理销毁——全库加密本身就是最强的介质级擦除手段[249][250]。

8.2.2 内存侧

内存侧停留时间由架构决定而非配置决定。page cache 明文页与连接同生命周期：codec 读出即解密入缓存，52pojie 对微信 PC 版数据库的逆向也证实 codec 内部存在明文 buffer——常驻进程的密钥必然以可用形态存在于内存[1][252]。SQLCipher 始终对密码学内部分配做锁定与 free 前清零，关连接时密钥材料随 codec 上下文被擦除；cipher_memory_security=ON 扩展到全部分配，但 4.5.0 起因性能代价默认关闭、开启后不可逆[2][212][8]；sqlite3mc 的 PRAGMA memory_security = 1 只做 free 前清零、不做 mlock，需编译期选项否则为 no-op[34]。密钥副本驻留最易误判：raw key 经 better-sqlite3 传入时至少存在一份 JS Buffer 加一份原生副本，UKey 拔出后仍在进程内，直到连接关闭或进程退出——"拔 UKey 即锁库"不成立，须主动 close() + fill(0)[34][253]。V8/JSC 堆中结果字符串、绑定参数不可变无法清零，GC 只回收不擦除，堆快照可完整捕获[253][254]。swap/休眠镜像则是以上一切的落盘投影，换出后直到被覆写，休眠镜像关机后仍在磁盘[226][227]。

表中呈现清晰的"清除能力分层"：磁盘侧除 SSD 残影外全部可达 A 级，因为清除动作（VACUUM、checkpoint、禁 temp 落盘）都在 SQLite 与 OS 的文档化能力之内；内存侧整体下沉到 B/C 级——page cache 与密钥副本需应用自建看门狗，V8 堆受 GC 语义限制无法保证零化。两个"有陷阱"的 A 级项需单独强调：WAL 模式下"开了 secure_delete ≠ 已删数据消失"，须叠加 checkpoint 截断与定期 VACUUM 才闭环[248]；temp_store=MEMORY 消除落盘的同时移除了内存上限承诺，大查询场景需压测确定水位[236]。A 档完整清单还包括 coredump 三层封堵、ptrace_scope=2、日志脱敏、依赖锁定加代码签名、UKey PIN 策略确认[219][225][217][237][239]；B 档另有静态链接 OpenSSL/sqlite3mc 缩小 LD_PRELOAD 面、容器 --ulimit core=0 与 drop 全部 capability[229][223]。

8.3.2 残余风险声明

三项风险在当前架构下无解，必须写入威胁模型文档而非回避。其一，root/CAP_SYS_PTRACE 内存读取：主机沦陷后一切用户态防护失效，page cache 明文与密钥副本全暴露，只能靠主机加固与入侵检测降低概率[217][218]。其二，Frida 级运行时 hook：可按偏移 hook 未导出的 codec 内部函数直接 dump raw key，反调试与混淆只提高成本[231]。其三，V8/JSC 堆明文不可彻底清除：字符串不可变与 GC 不零化是运行时语义，只能减少驻留量（Buffer 化流转、缩短对象生命周期），无法给出清除保证[253][254]。UKey 导出 raw key 瞬间的主机内存暴露属同一性质：除非改用卡内运算、永不导出的硬件方案，该窗口无法消除。这四项残余风险不推翻第 7 章的选型结论——给定"拷走文件不可读"的目标，SQLCipher v4/sqlite3mc + raw key + UKey 达标——但划定了适用边界：本架构防御的是离线攻击者，不是同主机在线攻击者。

9. 腾讯 WCDB 专题与迁移接入

第 2 章已把腾讯 WCDB 列为国产开源代表（11,618 Stars、BSD-3-Clause、v2.1.16 活跃维护、加密经内嵌 SQLCipher 实现）[54]。鉴于它是微信全端在用的终端数据库、且在加密修复/备份方向有业界稀缺的能力，本章单独展开：9.1 节解析其架构、加密实现、特色能力与风险，9.2 节给出各平台接入、与 SQLCipher 生态互通、三条迁移路径、Node.js 侧结论与密钥管理集成。

9.1 WCDB 深度解析

9.1.1 架构演进：从三套实现到统一 C++ 核心

WCDB v1.x（2017-06 开源）同时提供 Objective-C/Swift/Java 三种语言接口，但三套代码除"共用同一版本 SQLite、共用同一套备份修复逻辑"外完全独立开发，新能力基本只在 ObjC 版落地，Swift/Java 版长期停更[256][257]。v2.x 于 2019 年启动重写、放弃接口向后兼容，2024-04-09 正式官宣：因 ObjC 版核心本就是 C++ 实现，顺势将核心逻辑完全 C++ 化，Swift/Java/Kotlin 经 C Bridge 桥接层接入同一核心（Kotlin 直接复用 Java 实现），形成 C++/Java/Kotlin/Swift/ObjC 五语言薄绑定；不同语言可集成进同一项目操作同一数据库而无逻辑冲突[256]。平台覆盖 iOS/macOS/Android/Windows/Linux/OpenHarmony（Windows 于 v2.0.2、OpenHarmony 于 v2.1.7、Mac Catalyst 于 v2.1.15 加入）[54][258]。v2.x 自我定位为"纯 ORM 框架"，官方明确表示对适配 Room 兴趣不大[259]。

需要特别注意其 SQLite 版本跟随策略：WCDB 不直接跟随上游 SQLite/SQLCipher，而是跟随腾讯自维护的 Tencent/sqlcipher fork（git submodule 形式逐文件编译进 WCDB，CocoaPods 上以 WCDBOptimizedSQLCipher 发布）[54][260]。实测该 fork 在 WCDB 当前 submodule 指针（f049bed，2025-11-11 更新）处 CHANGELOG 顶端仍为 SQLCipher 4.1.0（基线 SQLite 3.27.2，2019-03），腾讯在此基线上叠加自有补丁（异步 checkpoint 钩子、崩溃修复等）[260]。即 WCDB 的加密基线明显滞后于上游（上游 SQLCipher 已到 4.6.x 代际），这是选型时必须计入的事实。

9.1.2 加密实现：接口极简，文件即标准 SQLCipher 格式

v2.x 的加密接口被压缩为一个方法：setCipherKey(key, pageSize=4096, cipherVersion=Default)，等价于依次配置 PRAGMA key（经 sqlite3_key() 下发）、PRAGMA cipher_page_size、PRAGMA cipher_compatibility；当前默认 cipherVersion = SQLCipher 4（256k 次 PBKDF2 迭代 + HMAC-SHA512），而 v1.x 时代默认为 3[263][264]。官方提供 canOpen() 接口，可在不确定建库参数时逐组配置探测[263]。v1.x 曾用 SQLiteCipherSpec 结构封装 cipher/pageSize/kdfIteration/hmacEnabled/版本号五个参数，同一结构可直接传给 RepairKit 复用[261][262]。未暴露的底层参数包括自定义 HMAC/KDF 算法、cipher_plaintext_header_size 与国密 SM4（issues #597、#1526）[265]。默认运行配置为 WAL 模式、synchronous=NORMAL、Apple 平台 fullfsync=1，且全平台统一 pageSize 4096（上游 SQLCipher 在 macOS 默认 1024）[263][266]。

由于底层就是 SQLCipher，WCDB 产出的文件即标准 SQLCipher 格式：参数对齐后可用 DB Browser for SQLite、sqlcipher CLI 等第三方工具直接打开，社区大量微信数据库解密实践依赖这一点[267][268]。WCDB 还把 sqlcipher_export() 扩展为双参数形式，支持密文↔明文双向互迁[269]。但 fork 与上游并非逐版本对齐：v1.x 的 setSQLCipherVersion(4) 曾被报"完全没法解密"（issue #834），说明个别版本存在行为偏差[265]。社区逆向整理的微信桌面端参数变迁恰好对应 WCDB 默认 cipherVersion 3→4 的演进：Windows 微信 3.x = SQLCipher v3 + page 4096 + kdf 64000 + SHA-1，4.0 起切换为 v4 默认（kdf 256000）；其中 4.0 的 HMAC 算法存在口径分歧——v4 默认值为 SHA-512，另有来源称 SHA-256，两说并存、本文并列呈现[267][270]。

9.1.3 特色能力：修复/备份三板斧是对加密场景的核心价值

WCDB 与加密正交的能力（WINQ 语言集成查询、FTS5 拼音分词、Zstd 字段级压缩、可中断事务）此处不展开[256][275]。对加密场景价值最高的是修复与备份链路全程兼容加密库——通用 SQLite 工具对加密损坏库基本无解，而 WCDB 的"三板斧"均可带密工作（需正确 key 与 CipherSpec）[271][272]：

  1. Dump 恢复：遍历 sqlite_master + SELECT * 导出 SQL，天然支持加密库，但成功率仅约 30%（master 表或第 0 页损坏即全灭）[271]；
  2. 备份恢复：自定义二进制格式 + 加密 + 多线程流水线，Android 微信在"充电并灭屏"时经 JobScheduler 触发，上线后恢复成功率 72%[271][272]；
  3. RepairKit（B-tree 解析恢复）：仿造只读最小系统（VFS 读 + SQLCipher 解密逻辑 + B-tree 解析）绕过 SQLite 引擎；因 salt 丢失会导致所有页无法解密，加密 salt 与 sqlite_master 一并纳入提前备份[271]。注意 RepairKit 并非对外公开接口[274]，且有用户报告加密库恢复率约 80%（issue #703）[265]。

v2 的全新备份方案采用分段按需 mmap（每次 map 1MB）+ LRU Cache + 读事务内零拷贝备份，增量备份依托自研异步 Checkpoint 低成本记录变更页号与叶子页 CRC（根页+中间页仅占 1~2%），500MB 库备份从 3 秒降到 63ms，10GB 库 <0.9s[257][273]。性能方面，官方口径（iOS、WAL、cache_size=-2000、page 4096、对比 FMDB）为读劣 5%、写优 28%、事务批量写优 180%[277]；加密本身的开销，SQLCipher 官方口径 5~15%，微信系工具文档口径 10~15%，并列呈现[260][267]。第三方来源可引用的数据点是微信实测现网 DB 损坏率约 0.02%、经同步策略优化后降低一半多[272]；而 2025-09 集中出现的一批"WCDB 快 2~3 倍""修复率 >90%"文章疑似 AI 生成，本报告不予采信[278]。

9.1.4 维护状态与风险

仓库实测（2026-07）：v2.1.16 发布于 2026-03-27，2025 年以来保持约每月一个小版本；v2.1.14 支持 Android 16KB 页、v2.1.7 支持 OpenHarmony，说明仍在跟进平台演进；贡献者 33 人[54][255][258]。License 为 BSD 3-Clause（版权方 THL A29 Limited），无额外专利条款，但随附第三方组件各自持证（Android 源码 Apache-2.0 含专利授权、SQLCipher BSD-3、OpenSSL 双许可等）[279]。风险有三：其一，SQLCipher 基线陈旧——2024-11 有用户指出 4.1.0 存在 CVE-2020-27207、CVE-2021-3119 并询问升级计划（issue #1245），修复以腾讯自行 backport 为主[260][265]；其二，公开可查的腾讯之外知名采用者很少，第三方多为中小 App[256]；其三，2.x 放弃向后兼容造成生态断代，1.x 停止迭代仍被广泛使用，形成事实上的两个生态[259]。文档侧官方 wiki 覆盖较全，但英文社区讨论稀少、issue 响应以关闭为主[280]。

最小接入代码（须在首次读写前设置密钥，否则按"无法解密"报错）：

// Android / Kotlin —— WCDB 2.x 新接口
import com.tencent.wcdb.Database
import java.nio.charset.StandardCharsets

val database = Database(filePath)
// 密钥为 byte[]（非 String！）；默认 pageSize=4096, cipherVersion=默认(SQLCipher 4)
val password = "password".toByteArray(StandardCharsets.UTF_8)
database.setCipherKey(password)
// 官方建议用 canOpen() 探测密钥与参数组合是否正确，再进入业务读写
check(database.canOpen()) { "数据库密钥或加密参数不匹配" }
// 注意：若经 compat 层使用 AOSP 风格 API，务必自定义 DatabaseErrorHandler——
// 默认实现会把"打不开的加密库"误判为损坏库并执行重命名/删除

// iOS / macOS / Swift —— WCDB 2.x
import WCDBSwift

let database = Database(at: filePath)
// 接口原型：setCipher(key: Data?, pageSize: Int = 4096, cipherVersion: CipherVersion = .defaultVersion)
database.setCipher(key: "password".data(using: .utf8)) // 须在首次读写前调用
assert(database.canOpen()) // 探测密钥/参数是否正确

9.2.2 与 SQLCipher 生态互通

互通的技术基础是"参数对齐即同一格式"。下表为 WCDB 参数与 SQLCipher PRAGMA 的一一对应：

WCDB 参数 SQLCipher PRAGMA 说明
cipherKey（byte[]/Data） PRAGMA key / sqlite3_key() 默认作为 passphrase 经 PBKDF2 派生
pageSize PRAGMA cipher_page_size WCDB 全平台默认 4096；上游部分平台默认 1024
cipherVersion（1/2/3/4） PRAGMA cipher_compatibility 覆盖 HMAC、KDF 迭代、算法组合
kdfIteration（1.x spec） PRAGMA kdf_iter v1/v2≈4000，v3=64000，v4=256000
hmacEnabled（1.x spec） PRAGMA cipher_use_hmac v1 默认关，其余默认开
cipher 算法 PRAGMA cipher 默认 aes-256-cbc

这张表是全部跨工具操作的"换算表"。两组兼容版本的参数组合须记牢：SQLCipher 3 = kdf 64000 + HMAC-SHA1 + PBKDF2-SHA1；SQLCipher 4（WCDB 2.x 默认）= kdf 256000 + HMAC-SHA512 + PBKDF2-SHA512 + page 4096[262][267]。由此推出三条可验证结论：WCDB 2.x 默认参数即 "SQLCipher 4 defaults"，DB Browser 3.12+ 直接选该项即可开库，非默认参数用"自定义"逐项填写、raw key 以 0x 前缀输入[294][292]；命令行 sqlcipher 依次执行 PRAGMA key、PRAGMA cipher_page_size=4096（必要时 cipher_compatibility）即可验证[295]；SQLiteStudio 底层用 SQLite3MultipleCiphers，选 SQLCipher: AES 256 Bit cipher + 匹配参数亦可打开[34]。唯一的例外是历史版本：1.1-19 时代的 WCDB 曾有 salt/派生差异导致与官方 SQLCipher 4 不完全对齐（issue #834），2.x 默认已与 SQLCipher 4 默认一致[296]。

对服务端（Node/bun），打开 WCDB 创建的加密库等价于"用 sqlite3mc 模拟 SQLCipher 4 兼容模式"：

// 服务端读取 WCDB 移动端生成的加密库 —— better-sqlite3-multiple-ciphers（sqlite3mc 内核）
import Database from "better-sqlite3-multiple-ciphers";

const db = new Database("/path/to/wcdb-created.db");
// 三行 PRAGMA 顺序不可乱：先选 cipher 方案，再设兼容版本与页大小，最后下发密钥
db.pragma(`cipher='sqlcipher'`);   // sqlite3mc 的 SQLCipher 兼容方案
db.pragma(`legacy=4`);             // WCDB 2.x 默认 = SQLCipher 4（kdf 256000 / HMAC-SHA512）
db.pragma(`cipher_page_size=4096`);// WCDB 全平台统一 4096
db.pragma(`key='${process.env.DB_PASSPHRASE}'`); // 与移动端一致的 passphrase（或 raw key）
// 验证可读；报错 "file is not a database" 即参数不匹配
console.log(db.prepare("SELECT count(*) FROM sqlite_master").get());

9.2.3 三条迁移路径

明文 SQLite → WCDB 加密库：官方推荐 ATTACH + sqlcipher_export()，无独立"一键加密 API"。在已打开的加密库上执行 ATTACH DATABASE '/path/old.db' AS old KEY ''; 附加明文旧库，再 SELECT sqlcipher_export('main', 'old');——注意 WCDB 扩展了该函数，第二参数可指定源库实现反向导入[285][297]。迁移后按旧库 user_version 走 onUpgrade/onDowngrade，确认无误再删旧文件。若库结构也要调整，可用 2.x 的框架级数据迁移（addMigration + enableAutoMigration/stepMigration）：开发者"假定迁移已完成"直接读写目标库，WCDB 后台每 2 秒迁约 0.01 秒直至完成，支持进度回调与过滤条件；迁移加密源库时需在 addMigration 传入源库密码，且源库只能走 setDefaultCipherConfiguration 的进程级默认加密配置（ATTACH 时只能传 key）[298][299]。已知缺陷：2.1.15 在"加密目标 + 明文源"场景 ATTACH 不带 KEY 存在 bug（issue #1545，2026-05 仍 open）[265]。

既有 SQLCipher 加密库 → WCDB：文件格式相同，参数匹配即可直开、无需转格式。1.x 风格写法是 new SQLiteCipherSpec().setPageSize(1024).setSQLCipherVersion(3) 配 openOrCreateDatabase(path, passphrase.getBytes(), cipher, ...)；2.x 等价于 setCipherKey(passphrase.getBytes(), 1024, CipherVersion.version3)[285][284]。五个要点：密码转 byte[]；参数必须与建库时完全一致，否则报"文件已损坏/不是数据库"；务必自定义 DatabaseErrorHandler——默认实现会把打不开的库当损坏库重命名/删除，密钥错误直接演变成数据丢失；删掉原 SQLCipher 的 loadLibs()；先 canOpen() 灰度验证再上线[285]。

WCDB 1.x → 2.x：2.x 是放弃向后兼容的重写[301]。Android 坐标从 wcdb-android 换成 main/annotation/compiler，不想改旧代码就加 compat 模块把 import 改为 com.tencent.wcdb.compat.*，旧 SQLiteDatabase 对象可经 getInnerDB() 拿到 2.x Database 混用[283][302]。iOS pod 从 WCDB 换成 WCDB.swift/WCDB.objc，查询 API 有变更[303]。最关键的加密坑是默认值切换：1.x 默认 SQLCipher 3，2.x 默认 SQLCipher 4——沿用 1.x 建的加密库必须显式 setCipherKey(key, pageSize, CipherVersion.version3)（1.x 时代 page 可能是 1024 或 4096），否则打不开；微信自身做法也是以创建时版本参数打开旧库、新库才用 v4[284][264]。数据文件本身无需转换，纯接口层迁移。

9.2.4 Node.js / 服务端结论

WCDB 不适用于 bun/Node 服务端，依据有三：官方自我定位为"移动/终端数据库框架"，五种语言接口全部是客户端语言，README/wiki 无任何 JavaScript 绑定或 Node 支持计划[256][269]；npm registry 实测（2026-07-27）wcdb 包名 404、全站搜索 0 结果，不存在官方或实质可用的 Node 绑定[304]；理论上可将 C++ 核心自行封装为 N-API addon，但成本远高于直接选用 Node 原生生态。服务端正解仍是第 7 章给出的 better-sqlite3-multiple-ciphers（sqlite3mc 内核）；老分支 better-sqlite3-sqlcipher 多年未维护、无法在现代 Node 上编译，应避免[163]。

但"一端 WCDB（移动端）+ 一端 sqlite3mc（服务端）"的跨端架构成立：两侧共享同一 SQLCipher v4 文件格式与同一密钥，数据库文件可直接双向拷贝使用。这正是 9.2.2 节 ts 示例对应的部署形态：

9.2.5 密钥管理：byte[] 接口与 raw key 对接 UKey/KMS

WCDB 各语言加密接口统一收字节密钥（Android byte[]、Swift Data、ObjC NSData*、C++ UnsafeData），不内置任何 KMS/Keystore 对接，密钥来源完全由应用层负责[284][264][289][263]。默认语义是 passphrase：SQLCipher 内部经 PBKDF2 派生真实密钥（v4 = PBKDF2-HMAC-SHA512 × 256000，salt 存于库文件头 16 字节）[267]。由于字节最终原样传给 sqlite3_key()，SQLCipher 的 raw key 机制同样生效：传入 ASCII 形式的 x'<64 hex>'（32 字节密钥直用、跳过派生）或 x'<96 hex>'（密钥 + salt 指定），即可把 UKey/KMS 下发的真实密钥直接注入而不经口令派生[2][137]；微信 PC 端正是用外部下发的 32 字节 raw key 直接加密数据库的实例[267][292]。推荐集成模式为：启动时从 UKey/KMS 取回密钥字节 → setCipherKey → canOpen() 校验 → 用完即弃内存副本。两个边界须知晓：WCDB 没有密钥回调/provider 抽象，也没有按表/按连接动态换钥的钩子；rekey 是高成本操作，官方明确提醒慎重使用[284]。进程级默认加密配置可用 setDefaultCipherConfiguration() 修改，服务于 ATTACH 加密库等只能传 key 的场景[298]。

本报告的结论建立在公开资料交叉验证之上：高置信结论均经两个以上独立维度证实，单一来源论断已标注置信等级。但调研过程中仍发现多处无法闭环的数据缺口与口径冲突，本章如实列出，供读者判断结论的适用边界。
