02 · 提示词注入lead 与 teammate 各自被注入了什么

报告第 3 章 · 依据 Piebald-AI 提示词模板仓库逐版本提取的七份 team 相关模板（ccVersion 跨度 v2.1.16–v2.1.203）。注入高度不对称：teammate 侧四重注入，lead 侧仅两处；lead 两处皆为负向约束（"不要 spawn""交付前必须 shutdown"），teammate 四重多为正向义务（认领任务、上报完工、等待审批）。点击条目展开对应提示词英文原文（逐字取自模板）。

Team Lead（主会话）

仅两处注入 · 无身份断言，team 于首个 teammate spawn 时隐式形成
Agent 工具的 spawn 抑制段v2.1.178▸
**Do not spawn agents unless the user asks.** Each spawn starts cold and re-derives context you already have — it's the expensive path on this plan. A task with "multiple angles," "thorough," or several parts is not a request to spawn; handle it inline with your own tools. Only use this tool when the user explicitly says to use a subagent, or names one of the available agent types.

Teammate

四重注入 · reminder + 常驻段双重断言 "You are a teammate"
身份与路径 reminder（TEAM_OBJECT 三字段）v2.1.178▸
<system-reminder>
# Team Coordination

You are a teammate in this session's agent team.

**Your Identity:**
- Name: ${TEAM_OBJECT.agentName}

**Team Resources:**
- Team config: ${TEAM_OBJECT.teamConfigPath}
- Task list: ${TEAM_OBJECT.taskListPath}

**Team Leader:** The team lead's name is "team-lead". Send updates and completion notifications to them.

Read the team config to discover your teammates' names. Check the task list periodically. Create new tasks when work should be divided. Mark tasks resolved when complete.

**IMPORTANT:** Always refer to active teammates by their NAME (e.g., "team-lead", "analyzer", "researcher"). Use an `agentId` (format `a...-...`, from the spawn result) only to resume a background agent that has already completed.
</system-reminder>

TEAM_OBJECT 仅含三个插值字段——agentName、teamConfigPath、taskListPath：teammate 被告知的不是协议细节，而是两个磁盘路径，"只给路径不给内容"，协作的 ground truth 在文件系统。lead 名硬编码为 "team-lead"（模板常量）；寻址分两层——活跃 agent 以 NAME 寻址，agentId 仅用于恢复已完成的 background agent。

常驻系统提示段 "Agent Teammate Communication"v2.1.173▸
# Agent Teammate Communication

IMPORTANT: You are running as an agent in a team. To communicate with anyone on your team, use the SendMessage tool with `to: "<name>"` to send messages to specific teammates.

Just writing a response in text is not visible to others on your team - you MUST use the SendMessage tool.

The user interacts primarily with the team lead. Your work is coordinated through the task system and teammate messaging.

区别于一次性 reminder，此段常驻 teammate 每次请求的 system 部分。三句话各承担一种约束：SendMessage 为唯一沟通通道；明文输出对队友不可见（"you MUST use the SendMessage tool"）；权威拓扑——"user interacts primarily with the team lead"，teammate 不应期待用户直接对话，状态须上报 lead。

TaskList "Teammate Workflow" 五步自我认领v2.1.38▸
## Teammate Workflow

When working as a teammate:
1. After completing your current task, call TaskList to find available work
2. Look for tasks with status 'pending', no owner, and empty blockedBy
3. **Prefer tasks in ID order** (lowest ID first) when multiple tasks are available, as earlier tasks often set up context for later ones
4. Claim an available task using TaskUpdate (set `owner` to your name), or wait for leader assignment
5. If blocked, focus on unblocking tasks or notify the team lead

TaskList 工具描述尾部条件性追加段。可认领条件为 pending + 无 owner + 空 blockedBy 三元组；认领即 TaskUpdate 设 owner，实现层对应 per-task lockfile 原子写。注意第 3 步"低 ID 优先"仅是文案层约定——HitCC 静态分析显示实现层 auto-claim 消费的是 readdir 顺序（QD() 不排序），文案与实现存在落差。

plan 审批硬阻塞 reminderv2.1.173▸
Your plan has been submitted to the team lead for approval.

Plan file: ${PLAN_FILE_PATH}

**What happens next:**
1. Wait for the team lead to review your plan
2. You will receive a message in your inbox with approval/rejection
3. If approved, you can proceed with implementation
4. If rejected, refine your plan based on the feedback

**Important:** Do NOT proceed until you receive approval. Check your inbox for response.

spawn 时带 plan 要求的 teammate 在 ExitPlanMode 提交后注入。揭示 plan 审批的物质形态：plan 实体是磁盘文件，审批走 mailbox 消息（plan_approval_request/response，以 REQUEST_ID 配对）。"Do NOT proceed until you receive approval" 是硬阻塞语义；官方文档称之为"设计例外"——lead 自主审批 teammate 的 plan，不再上卷用户。

提示词之下的运行时身份层（§3.5）：pane teammate 经 CLI flags（--agent-id/--agent-name/--team-name 三件套强校验，另加 --agent-color、--parent-session-id）传入后调用 setDynamicTeamContext({ agentId, agentName, teamName, color, planModeRequired, parentSessionId })（HitCC 反混淆 + nwyin v2.1.47 二进制分析互证，AsyncLocalStorage 承载）。这六字段快照与 TEAM_OBJECT 三字段（agentName / teamConfigPath / taskListPath）是同一身份在运行时层与提示词层的两个投影——提示词层的路径由 teamName 派生。in-process 与 pane 两种 backend 收到的提示词注入完全相同：协作语义同构，真正差别只在执行进程位置。

04 · 消息流时序一条 SendMessage 的完整链路

写方 lockfile 加锁 → 写 inbox JSON（每条 O(N) 全量读写）→ 对端 poller ~1s 轮询（in-process 500ms tick）→ 协议分类 → role:"user" + <teammate-message> XML 注入。

① SendMessage

工具 schema {to, summary?, message}；≥v2.1.199 名字一致性校验

② lockfile 加锁

lockfile.acquire()；写路径均带锁，读路径无锁

③ 写 inbox JSON

读全量 → push envelope{from,text,timestamp,read:false,summary?} → 写回，O(N)

④ poller 轮询

lead 主 poller ~1s fire-and-forget；in-process teammate 500ms tick

⑤ 协议分类

审批类本地吞掉并标 read；文本/关闭/idle 类进入注入路径

⑥ 注入对话

role:"user" + <teammate-message teammate_id color> XML，turn 边界投递

故障点 A · 竞态吞消息

poller 先无锁取 unread 快照（G$6），最后由 No6 重读当前文件把此刻所有 unread 全量标 read——落在快照与标读之间的新消息"不被处理却被标已读"，被静默吞掉（HitCC 单源逆向，置信度中-高）。

故障点 B · summary / message 静默丢失

部分 teammate 只写 5–10 词 summary、message 正文留空（3-agent 团队实测 2/3 返回 summary-only）；UI 还会主动隐藏 idle_notification 正文——消息到了但没有内容。对策：spawn brief 显式约定"交付物放正文"。

05 · 持久化与生命周期资产的分裂命运

存活最久的是任务数据，最短命的是团队身份：协调状态（config + inbox）易失、随会话死亡；工作产物（任务板）持久、跨 resume 存活。

teams/{team}/config.json
members 数组、leadAgentId、pane IDs
会话期存活 → 会话结束自动删除
teams/{team}/inboxes/{agent}.json
envelope JSON array，读后标 read 不删
随 config 目录一并删除
tasks/{team}/{N}.json
状态机 pending → in_progress → completed
本地持久保留、从不上传 · cleanupPeriodDays 回收
tasks/{team}/.lock / .highwatermark
flock 互斥 / ID 自增游标
随任务目录持久（并发正确性承载点）
projects/**/claude_*.jsonl
tmux teammate 独立顶层文件；in-process 为 sidechain 条目
cleanupPeriodDays 保留期

in-process teammate 崩溃

纯内存状态 · 无 checkpoint
  1. 状态只存在于 lead 进程内存的 InProcessTeammateTask 对象（messages、abortController 等纯内存字段），经 AsyncLocalStorage 隔离
  2. 无任何 checkpoint 落盘路径；transcript 仅为 lead JSONL 内 isSidechain:true 条目
  3. lead 进程崩溃或退出 → 全部 in-process teammate 状态即时蒸发，/resume//rewind 结构性不可恢复
  4. 社区实测损失量级："崩溃即丢 20 分钟进度（无 checkpoint）"（brandonwie，单一作者观察）

tmux teammate 崩溃

僵尸残留 · 四步清理（issue #52139）
  1. 崩溃后 config.json 中该成员仍以 isActive: true 被追踪，阻塞 TeamDelete
  2. ① SIGKILL 孤儿进程（SIGTERM 被忽略）
  3. ② tmux kill-pane -t %<id>
  4. ③ 手工编辑 config.json 把 isActive 改为 false → ④ TeamDelete 才被接受
  5. 另有官方 "Orphaned tmux sessions" 条目：tmux ls 定位 + tmux kill-session；lead 侧无死亡信号——崩溃与静默、挂起不可区分

两个设计对照亮点 — 报告 §7.3 · 点击展开左右对照

① 文件信箱两种实现：原子单消息文件 vs 数组 O(N) 重写§7.3.1▸

OmO · 原子单消息文件

inboxes/{member}/{uuid}.json——每封消息一个原子 JSON 文件；投递时先落 .delivering-{uuid}.json 预留，经 promptAsync 实时投递成功则移入 processed/ 确认，失败回滚。本质是把邮箱实现成文件系统上的事务队列：原子写消除读改写竞态，预留与归档给出至少一次投递的显式确认语义，代价是更重的投递协议。

VS

CC · 数组信箱 O(N) 整体重写

单个 JSON 数组信箱，发送方在 lockfile 保护下全量读、push、全量写回，每条消息成本 O(N)；且存在"无锁快照读 + 全量标读"的竞态窗口——新消息落在快照与标读之间即被静默吞掉。换来实现极简与调试友好，代价由静默丢失承担。

同一约束（无 broker、磁盘为唯一共享面）下可靠性频谱的两端；OmO 侧也在 issue #5344 暴露"报告成功但 lead 读不到消息体"的新故障——文件事务队列的正确性同样依赖实现成熟度。

② 隔离默认相反：git worktree vs 共享 cwd + 文件所有权纪律§7.3.2▸

OmO · Team Mode 用 git worktree

允许为成员声明 "worktreePath" 开独立 git worktree（裸分支名被拒绝），并可叠加 tmux 面板可视化（每成员经 opencode attach 挂一个 pane，tmux 缺失不阻塞建队）——把隔离交给 git 设施，赌"物理隔离比提示词纪律可靠"。

VS

CC · 共享 cwd + 文件所有权纪律

所有 teammate 默认共享 lead 的当前工作目录，靠任务粒度的文件所有权纪律避免写冲突；isolation:"worktree" 参数在 v2.1.114 被静默忽略（issue #50280），worktree 隔离在 teams 语境下并未真正接通——把隔离交给纪律与审批，赌"模型会遵守所有权约定"。

共同天花板：issue #3940 揭示 Team Mode 所有成员仍是同一 opencode 进程内的子 session、共享父会话工作目录，git worktree 只是同一仓库的不同 checkout；CC 的 split-pane 形态虽给出独立 OS 进程，仍共享 cwd——"成员级进程与仓库双重隔离"双方都未解决。

血缘：OmO 由 YeonGyu Kim（code-yeongyu）2025-12-03 建库，v4.0 大重构后由 oh-my-opencode 更名 oh-my-openagent，截至 2026-07-24 约 66.5k star / 5.4k fork（Sustainable Use License 1.0）。omo-slim 由 alvinunreal 于 2026-01-15 创建（恰在 Anthropic 封禁事件后一周），约 7.3k star / 447 fork，MIT 许可，最新 release v2.2.8；作者自称 "a slimmed-down fork of oh-my-opencode"——砍掉仪式化管线（规划—评审—执行六个具名 agent 全砍、category 路由与 Team Mode 整体移除，hook 从 54–61 压到约 13–17），保留 7+1 agent hub-and-spoke（Orchestrator 唯一 primary + 7 个核心专家 subagent），同任务实测省约 24% token。选型读法：先定位自己在"原语极简—仪式完备—成本收敛"三角中的位置，再按表 7-1 逐行核对该极点已知的故障模式。

Team Mode 已知语义坑（社区 issue 证据，§9.3.3）：① 成员是 single-shot——收到消息不会自动再触发，未文档化的 workaround 是在成员提示词里写显式 WAIT 指令；② 任务板是前向状态机——只有任务 owner 能更新状态，且 completed 不能回退到 pending；③ 生命周期残留——team_create 派生的 bg_* 任务在团队删除后仍跨轮次发完成通知；④ 协调失败不 fail-closed——issue #5344 实测 team_send_message 报告成功、lead 却读不到消息体，社区要求"交付物不可验证即作废重开，不得从残缺输出中合成结论"。
ADR-001 · "把默认行为收回来"：slim 的设计判断标准写在 ADR-001——为 /reflect 加跨会话反思时选择"纯 prompt、零新代码"，理由是 "Smallest useful form——YAGNI"，连缓存都让 LLM 用现成 Read/Write 工具自管；同一 ADR 规定所有持久数据集中在一棵目录树，反思 JSON 做 session → weekly → monthly 层级聚合。第三方对其哲学的概括："它不是把能力砍掉，而是把默认行为收回来"——续跑、重试、视觉分析、Council 全部改为 opt-in（需手动 @council）。配套的 prompt 缓存安全体系（cache-safe-injection.ts、cache-monitor/、stabilizeRunningTaskParts() 与前缀稳定性测试）使约 150k tokens 的编排提示词尾部免于每轮重写。
