01 · EXECUTIVE SUMMARY

一页看懂结论

2026 年的开源格局已收敛为「一超一强一新」三层；你的场景（bun 打包 + UKey 密钥）有明确的最优路径。

选型结论

生产选型只有两条成熟路径

SQLCipher 系（7,213★，事实标准，移动端验证最充分）与 SQLite3MultipleCiphers 系（661★，下游覆盖最广、2026 最活跃，可读写 SQLCipher/sqleet 文件）。Turso 原生加密仍 experimental，适合新项目试水。

你的场景

bun compile + better-sqlite3-multiple-ciphers

加密库以 raw 32 字节 key 直开（对接 UKey 零摩擦），Drizzle 经 npm alias 无缝接入；.node 原生模块作为 asset 嵌入单文件、启动时解包 dlopen——Claude Agent SDK 官方同款模式。

性能认知

两个独立的成本轴，别混为一谈

KDF 只在打开连接时发生一次（SQLCipher 25.6 万迭代 ≈ 手机端 100–120ms，UKey 直供 raw key 可完全跳过）；稳态开销与访问页数成正比——索引查询 2–5%，全表扫描可达 5 倍。

威胁模型

文件级加密防「拷走」，不防「本机」

微信 PC 的实践证明：常驻进程的密钥必然以可用形态存在于内存，逆向社区 30ms 可提取。你的 UKey 方案已解决密钥来源问题，防御目标应明确定位为静态文件失窃 + 泄漏兜底。

03 · HOW IT WORKS

加密 / 解密运行过程

所有主流方案同构：在 pager 层挂接 page-level codec，读页时解密、写页时加密，内存中恒为明文，落盘恒为密文。

(raw key 模式跳过 KDF) App->>Pager: 第一条 SQL（触发验钥） Pager->>Disk: 读取密文页 Disk-->>Pager: 密文页 + 页尾 IV/tag Pager->>Codec: 验证 HMAC/AEAD → 解密 Codec-->>Pager: 明文页入 page cache Pager-->>App: 返回查询结果 Note over App,Disk: 密钥错误时此刻才报 SQLITE_NOTADB(26)

04 · PERFORMANCE

性能：两个成本轴

脱离连接模型谈「性能损失 X%」没有意义。你的场景（UKey 直供 raw key）天然消除第一条轴。

轴一 · 打开成本（一次性）

KDF 迭代 ≈ 每次连接的固定延迟

SQLCipher v4 默认 25.6 万次 PBKDF2，手机 CPU 实测外推约 100–120ms/次打开。高频短连接场景（serverless、CLI）这条轴主导延迟。使用 32 字节 raw key（UKey 场景）可完全跳过 KDF，打开零成本——代价是密钥熵管理责任转移给你，UKey 恰好解决这一点。

轴二 · 稳态开销（与访问量成正比）

查询形态决定放大倍数

第三方实测（Nokia 6.1）：事务内 Insert +2.3%、索引 Select +3.4%、非索引全表扫描 +496%。长连接服务端应关注这条轴——索引设计比加密方案本身更影响稳态性能。

各方案实测 / 宣称一览

关键选型提示：无 AES-NI 的平台（部分 ARM/嵌入式）软件 AES 慢约 28 倍，应选 ChaCha20-Poly1305（sqlite3mc 默认）；x86 服务器有 AES-NI，AES-256 与 ChaCha20 差距不大。事务批量写入、4K 页、WAL 模式均可显著摊薄开销。

05 · DRIZZLE ORM

Drizzle 接入：三条路径

运行时层三条路径都透明；真正的接入成本在 drizzle-kit 工具链。

路径做法适用关键约束
A · libsql 驱动 createClient({url:'file:x.db', encryptionKey}) 后 drizzle(client) 最快上手；Turso 生态 bun compile 下有打包障碍（见下节）；replica 模式加密有未修复 bug
B · better-sqlite3-multiple-ciphers npm alias 顶替 better-sqlite3，Drizzle 零改动 你的场景推荐；Electron/服务端主流 PRAGMA 顺序强制 cipher→legacy→key，须在首条 SQL 前
C · sqlite-proxy Drizzle 生成 SQL 经 callback 发给加密后端 Tauri / 移动端 db.transaction() 不可用，须用 db.batch()

路径 B 最小接入示例（对应你的场景）

// package.json —— npm alias 无缝顶替
// "better-sqlite3": "npm:better-sqlite3-multiple-ciphers@^12"

import Database from 'better-sqlite3-multiple-ciphers';
import { drizzle } from 'drizzle-orm/better-sqlite3';

const sqlite = new Database('app.db');
// PRAGMA 顺序固定，且必须是打开后的第一条语句
sqlite.pragma(`cipher='sqlcipher'`);   // 默认 sqleet 可省略；选 sqlcipher 兼容工具链
sqlite.pragma(`legacy=4`);            // 兼容 SQLCipher v4 文件格式
sqlite.pragma(`key="x'${keyFromUKey}'"`); // UKey 读出的 32 字节 raw key（hex），跳过 KDF

const db = drizzle({ client: sqlite }); // 之后所有 ORM 操作与常规 SQLite 完全一致
最大的坑在 drizzle-kit，不在 ORM：push / migrate / studio / pull 均无加密参数，对加密库一律 SQLITE_NOTADB（issue #3198，提出 20+ 个月仍 open）。标准解法：CI 中 drizzle-kit generate（离线生成 SQL，不受影响）+ 应用启动时用 drizzle-orm/libsql-migrator 或 better-sqlite3/migrator 在 key 之后跑 migrate()。另外 bun:sqlite 与 node:sqlite 均不支持加密，:memory: 库不能 key。
06 · CASE STUDY

微信 PC 客户端是怎么做的

微信是「客户端 SQLite 加密」最成熟的量产案例。以下技术细节来自逆向工程社区（看雪/吾爱破解/GitHub 开源工具）的公开分析，非腾讯官方披露。

PC 3.x（Windows）PC 4.0（Win/Mac 统一）
引擎 SQLCipher v3 参数（腾讯 WCDB 内嵌变种） SQLCipher v4 默认（PBKDF2-SHA512 ×256,000，HMAC-SHA512）
文件布局 WeChat Files\<wxid>\Msg\：MicroMsg.db + MSG0~n.db 分片（约 240MB/片） xwechat_files\<wxid>\db_storage\：按业务域分库，message_0~9 分片，消息体再叠 ZSTD 压缩
密钥派生 每账号 × 每设备随机生成的 32 字节 raw key —— 不从口令派生、不依赖设备指纹
密钥存储 不落盘，仅内存常驻（4.0 内存中甚至存在 x'<key><salt>' 明文格式）
密钥管理的真相：所有社区工具（PyWxDump 基址偏移、wechat-dump-rs 特征扫描、lldb/WinDbg 断点）都从运行进程内存提取密钥，Windows 下最快 30ms 可得。混淆、反调试、版本快速迭代只提高成本、不改变结局。反例是 Android 端旧方案 key = MD5(IMEI+UIN) 取前 7 位且 IMEI 可获取——可离线推导，等于没加密。

深挖：WCDB 本身值得知道的五件事

维度结论
架构v2.x = 统一 C++ 核心 + 五语言薄绑定（ObjC/Swift/Java/Kotlin/C++），覆盖 iOS/macOS/Android/Windows/Linux/OpenHarmony；SQLite 不跟随上游，跟随腾讯自维护的 SQLCipher fork
加密实现接口只暴露 key / pageSize（4096）/ cipherVersion（默认 v4 = 256k 迭代 + HMAC-SHA512）；文件即标准 SQLCipher 格式。但内嵌 fork 基线停在 SQLCipher 4.1.0（2019），落后上游、靠腾讯自行 backport——CVE 修复跟随速度是引入前必须自评的信任问题
差异化价值修复/备份三板斧（Dump → 备份 → RepairKit + mmap 增量备份，500MB 库备份 63ms），全链路兼容加密库——这是它相对裸 SQLCipher 对加密场景独有的核心价值；另有 FTS5 拼音分词、WINQ
接入Android：com.tencent.wcdb:main:2.1.16 + setCipherKey(byte[], 4096, v4) + canOpen() 验钥，旧代码走 compat 模块改 import；iOS：SPM + setCipher(key: Data)；Windows/Linux 仅 C++ 接口
迁移明文→加密：ATTACH + sqlcipher_export 或 2.x 框架级 addMigration 渐进迁移；既有 SQLCipher 库：参数匹配即直开，务必自定义 DatabaseErrorHandler 防误判损坏删库；WCDB 1.x 旧库须显式指定 CipherVersion.version3
对你的 Node/bun 服务端：WCDB 不适用——五语言接口无 JS 绑定，npm 上无官方包（实测 404）。但这给出一个可行的跨端架构：移动端 WCDB + 服务端 better-sqlite3-multiple-ciphers，同一 SQLCipher v4 文件、同一密钥，两端互通（服务端配置 cipher='sqlcipher' + legacy=4 + cipher_page_size=4096）。密钥接口统一收 byte[]/Data，支持 x'64hex' raw key 形式，可直接对接 UKey/KMS 下发的真实密钥。

对你场景的三条启示

  • 密钥来源比算法重要——微信 PC 用「随机 key + 内存常驻」，你的「UKey 注入 raw key」在密钥来源上已经更强：密钥不经口令派生、不依赖机器指纹、拔出即失效。这一步选对了。
  • 算法直接照抄 SQLCipher v4 默认参数即可（AES-256-CBC + HMAC-SHA512；raw key 模式连 KDF 都不需要）——这是被 Signal、微信等亿级产品验证过的参数组合，没有自研理由。
  • 混淆/打包只挡脚本小子——bun compile 产物的内嵌 JS 可被 marker 轻易提取，切勿把任何秘密编译进二进制；防运行时内存 dump 要靠部署侧补足（禁 ptrace/core dump、UKey 拔出停服、文件 0600 权限）。

混淆的定位：保护 IP，而非保护密钥

密钥来自 UKey 时，混淆不保护密钥本身，只抬高 UKey 交互逻辑与业务代码的静态逆向门槛。注意 bytenode 依赖 V8、在 Bun 不可用；javascript-obfuscator 在 Bun 下可运行但慢约 7 倍（bun #1421），建议只对敏感模块混淆而非全量。

防御闭环检查单：
  • at-rest 加密：数据库文件被拷走 → 无 UKey 无法解密 ✓
  • 密钥来源：UKey 注入 raw key，二进制中无任何秘密 ✓
  • 密钥使用：raw key 模式跳过 KDF，打开零延迟 ✓
  • 运行时防护（部署侧）：禁 ptrace / core dump、UKey 拔出停服、文件 0600 权限 —— 需在部署文档中落实

位置形态停留时间清除方式与残留风险
主库 / WAL / journal密文永久freelist 中已删数据持 key 可恢复、无 key 不可读；WAL 模式下 secure_delete 要等 checkpoint + 截断才真正生效（DFRWS 实验：旧帧可完整恢复）
temp 文件（排序/瞬时索引）明文语句执行期间每连接 PRAGMA temp_store=MEMORY（有内存代价）；删除后 SSD wear-leveling 残影覆写不可靠——防残影的正确解是加密本身（加密擦除）
导出 / 备份产物明文直到显式删除authorizer 禁用导出路径；确需备份走加密→加密（SQLCipher 4.3+ backup API 仅支持加密→加密）
page cache（内存）明文连接整个生命周期关闭连接即释放；无法避免——这是所有页级加密的架构必然
密钥副本（内存）明文UKey 拔出后仍在，直到 closeUKey 拔出即主动 db.close() + 密钥 Buffer fill(0)；密钥全程 Buffer 化，避免进入 JS 字符串（字符串不可零化）
V8 / JSC 堆（查询结果）明文不可预测（GC 不保证零化）JS 层无法可靠清除——接受为残余风险；缩小窗口：结果即用即弃、避免全局缓存查询结果
swap / 休眠明文落盘落盘后长期残留禁 swap 或 swap 加密 + 禁休眠；mlock 只覆盖常规换出

注意 PRAGMA secure_delete 的口径差异：标准 SQLite 默认 OFF，SQLCipher 官方构建默认编译开启（零填充已删页）；sqlite3mc 发行构建的默认值需实测确认，建议部署时显式 PRAGMA secure_delete=ON + 定期 VACUUM。

纵深防御检查单（按优先级）
  • 启动即 prctl(PR_SET_DUMPABLE,0)，叠加 ulimit / systemd / 容器四层 core dump 封堵
  • 每连接 temp_store=MEMORY + secure_delete=ON + authorizer 禁用 ATTACH / sqlcipher_export / VACUUM INTO
  • UKey 拔出 → db.close() + 密钥 Buffer fill(0)；密钥不进 JS 字符串
  • OS 层：禁 swap（或加密 swap）、禁休眠、文件 0600、发布物代码签名
  • 明确接受残余风险：root 内存读取、Frida hook、V8 堆明文——这三项在当前架构下无解，写入威胁模型文档而非假装不存在

诚实声明：本调研的数据缺口

  • sqleet / sqlite3mc 无量化官方 benchmark，仅定性结论；
  • Turso 加密性能（读 6%/写 14%）无第三方复现，且加密功能仍 experimental（无 rekey、无既有库迁移）；
  • libSQL embedded replica 模式存在加密被静默丢弃的上游 bug（副本实为明文），使用前必须实测；
  • better-sqlite3-multiple-ciphers 性能存在两组矛盾口径（70–75% vs ~18%），报告并列呈现、未做取舍；
  • 微信 PC 加密细节来自逆向社区公开分析，非官方口径，可能随版本变化。
